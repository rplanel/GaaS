# Requirements: GaaS — Galaxy as a Service

**Defined:** 2026-08-10
**Core Value:** Developers can reliably build, deploy, and operate custom Galaxy-powered web interfaces with clear observability, because structured logging makes runtime behavior understandable to both humans and LLMs.

## v1.3 Requirements

Requirements for the Analysis Usage Statistics milestone. The durable survival record already exists as the `analysis_monitoring` table; this milestone extends it into full per-user usage statistics. No new table, no new write path, no new dependencies.

### Schema & Survival

- [x] **SCHE-01**: `analysis_monitoring` gains nullable `workflow_name` and `galaxy_workflow_id` snapshot columns so per-workflow stats survive workflow deletion
- [x] **SCHE-02**: Add composite indexes `(owner_id, workflow_id)` and `(owner_id, started_at)` for the per-workflow and trend queries
- [x] **SCHE-03**: A migration backfills the new snapshot columns from existing data where available without guessing historical outcomes

### Write Path Integrity

- [x] **WRIT-01**: The persist path snapshots `workflow_name` and `galaxy_workflow_id` onto the `analysis_monitoring` row at creation
- [x] **WRIT-02**: Deleting an analysis finalizes its stranded `analysis_monitoring` row from `pending` to `cancelled`, guarded on `pending` so the sync task remains the sole terminal-state writer

### Stats Query Layer

- [x] **STAT-01**: A query-layer Effect helper returns per-user total analyses and success/error/cancelled/pending outcome breakdown (existing counts preserved)
- [x] **STAT-02**: A query-layer Effect helper returns per-workflow usage (GROUP BY workflow_id) for a user, using the snapshot workflow name
- [x] **STAT-03**: A query-layer Effect helper returns time-bucket trend series (date_trunc on `started_at`, UTC) for a user
- [x] **STAT-04**: A recorded success-rate definition (e.g. `success / total` or `success / (success + error)`) is chosen and applied consistently

### API Endpoints

- [x] **API-01**: The self endpoint `GET /api/db/analyses/monitoring` returns a backward-compatible `AnalysisMonitoringStats` including per-workflow usage and trend series
- [x] **API-02**: The admin endpoint `GET /api/db/analyses/monitoring/admin` returns the equivalent admin statistics
- [x] **API-03**: The self endpoint derives `ownerId` from the server-side Supabase session identity, never from client input
- [x] **API-04**: The duplicated admin-role check is extracted into a shared `requireAdminRole` Effect helper

### Testing & Gates

- [x] **TEST-01**: Tests cover aggregation SQL (per-workflow, trend, outcome counts)
- [x] **TEST-02**: Tests verify the delete-time finalization and that stats survive analysis deletion
- [x] **TEST-03**: Tests verify RLS/self-scoping prevents one user reading another's stats
- [x] **TEST-04**: Tests verify the admin gate rejects non-admin users
- [x] **TEST-05**: Root `pnpm lint`, `pnpm typecheck`, and `pnpm test` pass

## v2 Requirements

Deferred to a future release. Tracked but not in current roadmap.

### Usage Statistics UI

- **UIAU-01**: Each user can view their own usage statistics in the UI
- **UIAU-02**: An admin/operator can view global usage statistics across all users
- **UIAU-03**: The statistics view supports time-range and workflow filters

## Out of Scope

Explicitly excluded. Documented to prevent scope creep.

| Feature | Reason |
|---------|--------|
| Usage statistics UI | v1.3 is server + API only; UI deferred to v2 |
| Full append-only audit/log table | v1.3 delivers usage stats by extending `analysis_monitoring`; a parallel audit table duplicates tested machinery |
| Per-user quotas / billing enforcement | Not a stats-delivery concern; out of milestone scope |
| Real-time dashboards / WebSocket counters | Requires UI + change-event plumbing; deferred to v2+ |
| Pre-aggregated materialized rollups | Premature at current scale; query-layer aggregation is sufficient |
| Hourly time buckets | Coarse day/week/month buckets satisfy trend needs; hourly deferrable |
