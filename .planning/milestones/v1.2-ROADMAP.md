## Phase 6: Audit and Freeze the Sync Contract

**Requirements:** AUDIT-01, AUDIT-02, AUDIT-03

### Success Criteria

1. An inventory document lists every legacy `synchronize*Effect` call site and every client-side sync trigger, explicitly marking each as dead, redirected, or still running and noting what data it mutates.
2. The canonical server-driven sync contract is documented for `syncAnalysisEffect`, `syncJobEffect`, `syncOutputDatasetEffect`, and the `galaxy:sync-analyses` scheduled task, including inputs, outputs, lock semantics, TTL rationale, batch size, and terminal-state rules.
3. An evlog trace audit report identifies at least three concrete gaps in the current sync workflow (e.g., missing boundary logs, race windows, unhandled error branches, partial writes).
4. Audit findings are reviewed and signed off before any refactor code is changed.

## Phase 7: Standardize evlog Traces

**Requirements:** OBSERVE-01, OBSERVE-02, OBSERVE-03, OBSERVE-04

**Plans:** 2/2 plans executed

- [x] 07-PLAN.md — Standardize evlog traces across the canonical server-driven Galaxy sync path
- [x] 07-02-PLAN.md — Close verification gaps: sanitize lock-release error log and add missing state-transition boundary logs

### Success Criteria

1. Every sync boundary emits structured evlog logs via `Effect.logInfo`, `Effect.logDebug`, or `Effect.logError`: task start/end, lock acquire/release, Galaxy invocation fetch, analysis/job/dataset state transition, dataset download/upload, and all error paths.
2. All sync logs carry relevant annotations (`analysisId`, `ownerId`, `galaxyInvocationId`, `historyId`, `jobId`, `datasetId`) so a single trace can be reconstructed across child effects.
3. The scheduled task finalizer always emits a `taskLog.emit` wide event containing `synced`, `failed`, `skipped`, `durationMs`, and an error summary, including on early-return paths.
4. A static scan and test snapshot review confirm that no Galaxy API keys, Supabase service keys, JWTs, or dataset contents are logged in sync paths or tests.

## Phase 8: Consolidate and Harden the Server-Driven Sync Path

**Requirements:** REFACTOR-01, REFACTOR-02, REFACTOR-03, REFACTOR-04

**Plans:** 7/6 plans complete
**Wave 1**

- [x] 08-PLAN.md — Add sync-attempt columns and atomic lock RPC (tracer)

**Wave 2** *(blocked on Wave 1 completion)*

- [x] 08-02-PLAN.md — Wire sync lock TTL, batch size, and retry config through ModuleOptions
- [x] 08-04-PLAN.md — Add output dataset idempotency guard and verify failure isolation

**Wave 3** *(blocked on Wave 2 completion)*

- [x] 08-03-PLAN.md — Add bounded retry/backoff and sync-attempt tracking updates

**Wave 4** *(blocked on Wave 3 completion)*

- [x] 08-05-PLAN.md — Remove legacy Drizzle sync helpers and delete unused files

**Wave 5** *(blocked on Wave 4 completion)*

- [x] 08-06-PLAN.md — Add lock contention and batch summary tests; run root quality gates

### Success Criteria

1. Legacy Drizzle sync helpers (`synchronizeAnalysisEffect`, `synchronizeJobEffect`, `synchronizeHistoryEffect`, and the old output helper) are deleted and have no remaining call sites or tests.
2. `sync_locks` acquisition is implemented as an atomic upsert (e.g., `insert ... on conflict do nothing`), and both lock TTL and batch size are configurable via the nuxt-galaxy module options.
3. The `analyses` table has `sync_attempts`, `last_sync_error_at`, and `next_sync_at` columns; the sync Effect program implements a retry/backoff policy for transient Galaxy and Supabase failures.
4. Per-analysis failures are caught, recorded, and do not crash the batch sync task; locks are released via `Effect.addFinalizer` even when the sync fails.
5. Concurrent scheduled task runs produce no duplicate workers or unique-violation noise in the lock table.

## Phase 9: Remove Client-Side Sync Triggers and Add On-Demand Path

**Requirements:** CLIENT-01, CLIENT-02, CLIENT-03

**Plans:** 2/2 plans complete

Plans:
**Wave 1**

- [x] 09-01-PLAN.md — On-demand sync end-to-end tracer

**Wave 2** *(blocked on Wave 1 completion)*

- [x] 09-02-PLAN.md — Document Realtime contract and close UI backstops

### Success Criteria

1. No client component, composable, or page triggers Galaxy sync outside the scheduled task; any remaining triggers are removed or redirected to the server-owned path.
2. Supabase Realtime is documented in code comments and user-facing docs as a display-only refresh mechanism; the server task owns all sync state mutations.
3. A server action or API handler accepts a single `analysisId` payload and enqueues `galaxy:sync-analyses` without bypassing the lock table.
4. The on-demand path is covered by at least one integration test that verifies the lock is respected and no duplicate sync is started.

## Phase 10: Expand Test Coverage

**Requirements:** TEST-01, TEST-02, TEST-03, TEST-04

**Plans:** 1/1 plans complete

**Wave 1**

- [x] 10-01-PLAN.md — Expand server sync test coverage for lock contention, Galaxy unavailability, partial failure, and task-level summaries

### Success Criteria

1. Lock contention tests pass: a held lock causes the analysis to be skipped; an expired lock is reclaimed by a new worker.
2. Galaxy unavailability tests pass: a 503 response triggers retry and eventual success; repeated 503s mark the analysis failed and increment `sync_attempts`.
3. Partial failure tests pass: a DB write failure inside output sync releases the lock and allows the batch to continue.
4. Task-level summary tests return correct `{ synced, failed, skipped }` counts for mixed happy-path and failure outcomes.
5. All new tests pass and contain no secrets in logs or snapshots.
