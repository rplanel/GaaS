## Phase Details

### Phase 12: Schema & Survival Columns

**Goal**: The `analysis_monitoring` schema carries the durable fields and indexes that make per-workflow and trend statistics survive workflow deletion.
**Depends on**: Nothing (first phase of v1.3)
**Requirements**: SCHE-01, SCHE-02, SCHE-03
**Success Criteria** (what must be TRUE):

  1. `analysis_monitoring` rows expose nullable `workflow_name` and `galaxy_workflow_id` snapshot columns, so per-workflow stats remain correct after a workflow is deleted
  2. Composite indexes `(owner_id, workflow_id)` and `(owner_id, started_at)` exist and serve the per-workflow and trend queries
  3. Existing rows migrate cleanly: snapshot fields are backfilled only from known data, and historical outcomes are never guessed or fabricated
  4. Regenerated Supabase/type definitions compile against the extended schema

**Plans**: 2 plans

Plans:

- [x] 12-01-PLAN.md — Extend analysis_monitoring schema (3 nullable snapshot columns + 2 composite indexes), generate migration + append idempotent backfill, extend migration/schema test
- [x] 12-02-PLAN.md — Apply migration to local Supabase + regenerate Supabase types + typecheck (schema-push/type-sync gate)

### Phase 13: Write Path Integrity

**Goal**: New analyses record their workflow provenance at creation, and deleting an analysis finalizes its stranded monitoring row.
**Depends on**: Phase 12
**Requirements**: WRIT-01, WRIT-02
**Success Criteria** (what must be TRUE):

  1. A newly persisted analysis snapshots `workflow_name` and `galaxy_workflow_id` onto its `analysis_monitoring` row at creation
  2. Deleting an analysis finalizes its stranded monitoring row from `pending` to `cancelled`
  3. A real terminal outcome already written by the sync task (success/error) is never overwritten by deletion — finalization is guarded on `pending`
  4. The sync task remains the sole terminal-outcome writer for all non-delete transitions

**Plans**: 2/2 plans executed

Plans:

- [x] 13-01-PLAN.md — WRIT-01 create path: thread WorkflowSnapshot through analyses.post.ts → runAnalysis → insertAnalysis → the canonical insertAnalysisMonitoringEffect (snapshot + tx), delegate the inline monitoring insert, expand snapshot/NULL-passthrough/distinct-tx/controller tests
- [x] 13-02-PLAN.md — WRIT-02 delete path: pending-guarded finalizeAnalysisMonitoringEffect (pending→cancelled, located by analysisId+ownerId, returns row|undefined, evlog) wired into deleteAnalysis in one transaction after the Galaxy delete, expand finalize/guard/ordering/no-op/Galaxy-failure tests

### Phase 14: Stats Query Layer

**Goal**: Self and admin callers can query the four usage-statistic dimensions through typed Effect helpers.
**Depends on**: Phase 12
**Requirements**: STAT-01, STAT-02, STAT-03, STAT-04
**Success Criteria** (what must be TRUE):

  1. A per-user query returns total analyses and success/error/cancelled/pending outcome breakdown, preserving existing count behavior
  2. A per-user query returns per-workflow usage grouped by `workflow_id` using the snapshotted name, including an explicit `unknown` bucket for orphaned workflow ids
  3. A per-user query returns a UTC time-bucket trend series on `started_at` where bucket sums equal the total
  4. A single, documented success-rate formula yields the same value across all query paths

**Plans**: 3/3 plans executed

Plans:
**Wave 1**

- [x] 14-01-PLAN.md — Shared computeSuccessRate + per-workflow usage (GROUP BY workflow_id, snapshot name/version, single `unknown` orphan bucket, per-workflow successRate); self/admin parity; tests (tracer)

**Wave 2** *(blocked on Wave 1 completion)*

- [x] 14-02-PLAN.md — UTC time-bucket trend (date_trunc on started_at AT TIME ZONE 'UTC', day/week/month allowlist, data-derived range, continuous zero-fill, bucket sums = total); empty -> []; tests

**Wave 3** *(blocked on Wave 2 completion)*

- [x] 14-03-PLAN.md — Composite getAnalysisMonitoringStats/getAllAnalysisMonitoringStats assembling counts + perWorkflow + trend into additive AnalysisMonitoringStats with overall successRate; cross-path success-rate parity tests

### Phase 15: API Endpoints

**Goal**: Self and admin endpoints expose the composite statistics contract to server API consumers (no UI).
**Depends on**: Phase 14
**Requirements**: API-01, API-02, API-03, API-04
**Success Criteria** (what must be TRUE):

  1. `GET /api/db/analyses/monitoring` returns an `AnalysisMonitoringStats` object (extending existing counts) with per-workflow usage and trend series, and existing consumers keep working
  2. `GET /api/db/analyses/monitoring/admin` returns the equivalent admin statistics
  3. The self endpoint derives `ownerId` only from the server-side Supabase session identity — a request can never surface another user's stats
  4. Both endpoints use a shared `requireAdminRole` Effect helper, and a non-admin is rejected

**Plans**: 1/1 plans executed

- [x] 15-01-PLAN.md
