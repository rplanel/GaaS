    1. **Server API routes** (`packages/nuxt-galaxy/src/runtime/server/api/**/*.ts`)
       - API: `const log = useLogger(event)` from `evlog`
       - Context: set `handler`, `method`, `path` via `log.set({ ... })`
       - Errors: prefer `createError({ message, status, why, fix })` from `evlog`; log before throwing

       - API: `const taskLog = createRequestLogger({ operation, requestId })` from `evlog`
       - Wrap Effect programs with `runTaskEffect(taskLog, effect)`
       - Manual `taskLog.emit({ status })` at task completion
       - Never share loggers between task invocations

    3. **Client composables** (`packages/nuxt-galaxy/src/runtime/app/composables/**/*.ts`, `packages/ui/...`)
       - API: auto-imported `log` from `evlog/client` (Nuxt auto-import)
       - Prefer structured objects: `log.info({ action: '...', ...context })`
       - Transport opt-in via `evlog: { transport: { enabled: true } }` in `nuxt.config.ts`

    4. **Module lifecycle** (`packages/nuxt-galaxy/src/module.ts`, seed/migrate scripts)
       - API: `initLogger({ env: { service } })` or `createRequestLogger({ operation })`
       - Use `logger.withTag('nuxt-galaxy')` from `@nuxt/kit` for build-time diagnostics only
       - Runtime module wiring must use `evlog/nuxt` configuration, not manual top-level loggers

       - API: `Effect.logInfo`, `Effect.logError`, `Effect.logDebug`, `Effect.logWarn` inside `Effect.gen`
       - Routed into request-scoped logger via `runGalaxyEffect`/`runTaskEffect`
       - Severity mapping: `ERROR`/`FATAL` → error, `WARN` → warn, `DEBUG` → debug, default → info

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Source code → log file (`.evlog/logs/`) | Structured log output written to local filesystem; secrets must be redacted before crossing this boundary |
| User input → log context | Request bodies, params, headers, and Galaxy API responses may be logged as context; must be treated as untrusted |
| Effect program → evlog bridge | `Effect.log*` messages pass through `evlogEffectLogger`; sensitive fields in annotations/spans must not leak |
| Client → server ingest | `evlog/client` transport sends client logs to `/api/_evlog/ingest`; payload validation and origin checks required if enabled |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Information Disclosure | `.evlog/logs/` output | critical | mitigate | Document and enforce secret redaction (`redact: !isDev`); forbid logging `GALAXY_API_KEY`, service keys, tokens; verify in review checklist |
| T-01-02 | Information Disclosure | Structured errors returned to client | high | mitigate | Use `internal` field only for backend context; `toJSON()` must not expose `internal`; document in conventions |
| T-01-03 | Tampering | Log files on disk | medium | accept | Local FS drain is for development; production should use immutable external drains (future phase). Document trust assumption. |
| T-01-04 | Repudiation | Audit-worthy actions (analysis create/delete, role changes) | medium | transfer | Research notes that audit logs are out of scope for this phase; defer to Phase 2/ADOPT-02 via `build-audit-logs` skill |
| T-01-05 | Log Injection | `log.set({ ... })` with unsanitized user input | high | mitigate | Conventions must require explicit field selection; never `log.set({ body })`; include injection check in review checklist |
| T-01-06 | Elevation / Denial of Service | Client transport to `/api/_evlog/ingest` | medium | mitigate | If enabled, validate payload shape and origin; rate-limit; document opt-in behavior |
</threat_model>
