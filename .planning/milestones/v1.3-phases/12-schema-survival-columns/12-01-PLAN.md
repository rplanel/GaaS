|----------|-------------|
| migration runner (service/migrator) → galaxy schema | The DDL + backfill UPDATE execute as the migration runner (drizzle migrate with the GALAXY_DRIZZLE_DATABASE_URL connection), NOT as an end-user's authenticated role. Backfill writes rows regardless of the owner-scoped RLS policies. |
| drizzle schema file → generated SQL | The TypeScript schema declarations become raw DDL; a mistake here propagates to the real DB. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-12-01 | Tampering / Elevation | backfill UPDATE in migration.sql | medium | mitigate | The backfill runs in migration/service-role context (authoritative migrator), never as an end user, so RLS owner scoping is intentionally bypassed only during the trusted offline migration (RESEARCH Security). It is additive: only SETs the three new snapshot columns via COALESCE from the local workflows table; it cannot alter outcome/analysis/owner columns. |
| T-12-02 | Tampering | RLS policies on analysis_monitoring | medium | mitigate | Do not remove/replace any of the four pgPolicy() entries. drizzle-kit only emits ADD COLUMN/CREATE INDEX, never policy changes; Task 1 forbids touching the pgPolicy block. New nullable columns are automatically covered by the existing owner-scoped Select/Insert/Update policies. |
