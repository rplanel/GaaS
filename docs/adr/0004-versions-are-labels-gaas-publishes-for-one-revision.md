# Versions are labels GaaS publishes for one Galaxy revision

GaaS identified a workflow version by two Galaxy tags, `name:` and `version:`, and kept one Galaxy stored workflow per version: releasing a new version meant copying the workflow in Galaxy, retagging the copy and activating it as a new `workflows` row. Galaxy's own model puts the pieces elsewhere. Tags attach to the stored workflow, never to a revision (`StoredWorkflowTagAssociation`), so a stored workflow carries one `version:` tag at a time and retagging it for a release rewrites the label of the previous one; that is what forced the copy, and what the **retagged workflow** concept existed to report. Revisions are an append-only history that every editor save extends, immutable once written and addressed by a stable 0-based index (`get_internal_version`). The thing GaaS wants to label, one exact revision, has no slot in Galaxy at all. #48 made the tag model safe by pinning every activated row to the revision it was activated at, so nothing drifts any more; this decision is about where the label lives (#67).

We decided that **a version is a label an administrator publishes in GaaS for one revision of one Galaxy stored workflow**. The `workflows` table stays, one row per published version, carrying the stored workflow id, the revision index and its uuid, the name and the label, a snapshot of that revision's export, who published it and when, and an `active` flag. Labels are immutable: a change to a workflow, however small, is a new version. One stored workflow serves a whole lineage, so nothing is copied, Galaxy's own history shows the lineage, and the editor stays the only place edits happen. The `name:` and `version:` tags survive only as pre-fill in the publish dialog.

The label belongs to the release act, and the release act is GaaS's. Putting it where Galaxy cannot touch it removes the retagged workflow concept, its column, its tests and its glossary entry instead of fencing them further. Publishing becomes a reviewed act, with a tool check before anything is written, where a tag used to be checked only when activation refused it. And the moment is right: no production rows exist, #48 has closed the correctness hole so nothing is rushed, and few things read the schema. The redesign will never be cheaper than now.

## Considered options

- **Stay tag-based with #48's pinning**, adding a re-pin action and a retire switch. Ticket-sized, and everything correctness-related was already fixed. Rejected because it keeps a copy per version and keeps adding machinery whose only purpose is to paper over Galaxy having no slot for a release label.
- **Two tables, a lineage and its versions**, the shape #67 first drew. Rejected because nothing reads a lineage: results views, usage statistics and the sidebar all key on the two strings, and the glossary already reads each version as a workflow to the web application. A second table would nest every analysis query one level deeper for an entity with no attribute of its own. Revisit trigger: the day a lineage needs an attribute, such as a description or a default version.
- **Adoption**: re-pointing a label to a newer revision under a cosmetic-only rule, enforced by a compatibility diff that refuses any change to inputs, output labels, tools, parameters or connections. Rejected because with no copy to pay a new label is cheap, while adoption makes the label mutable, turns the diff into a gate the milestone has to build, needs an update policy on `revision`, and stops "1.0" meaning one thing. `analyses.workflow_revision` (#48) is kept so adoption could be added later without a backfill.
- **Writing the tags back to Galaxy at publish**, so the `.ga` export still carries the label. Rejected because GaaS writes no Galaxy metadata today, one tag can carry only the latest label, and it recreates the concept being removed. An author who wants the label in the `.ga` keeps the tag by hand.
- **A patch rung for results views**, reading dotted-numeric labels so `1.0/` covers `1.0.x`. Rejected because a label is a free string GaaS never parses, and without the diff nothing backs the guess that a patch never changes the view. A developer covers a patch label with a name-level view or a file that renders the previous version's view; the admin page's "fallback" reading is the signal to write one.

## Consequences

- **Schema.** `auto_version` becomes `revision`; `revision_uuid`, `published_at`, `published_by` and `active` are added; `unique(user_id, galaxy_id, revision)` replaces `unique(galaxy_id)`, since `user_id` names the Galaxy service user and therefore the instance and keeps the door to several instances open; `unique(name_key, version_key)` stays app-wide because a results view directory is. Nothing migrates: there are no production rows.
- **Immutability is the database's.** The admin update policy comes with a column-level grant that leaves `active` the only updatable column, in a hand-written migration like the RBAC one. An administrator may delete a version no analysis references; the foreign key from `analyses` refuses otherwise, and the already seeded `workflows.delete` permission is the policy. The seed gains `workflows.update`.
- **`active` means startable by users**, nothing else. The list query hides retired versions; a select policy must not, because `analysis.workflows` has to keep resolving for past analyses and their results views. Usage statistics are history over monitoring records and ignore the flag.
- **A name may span stored workflows**, so a workflow rebuilt from scratch in Galaxy continues its lineage under a new label. A stored workflow keeps one name once it has a version; the dialog locks it, a handler rule rather than a constraint.
- **The admin page** lists every stored workflow of the service account, published ones first; tags are no longer required. The publish dialog lists the revisions with index, update time and step count, defaults to the latest, shows published revisions disabled with their label, and lets any unpublished revision be published, an older one included, since labels are not ordered. The name is locked to the lineage, else pre-filled from `name:`, else typed; the label is pre-filled from `version:`, else typed; Galaxy's display name is never a pre-fill because it usually cannot name a directory. Both pass ADR 0003's directory rule before anything is written. Publish is disabled while a tool of the chosen revision is missing at its pinned version, which `require_exact_tool_versions` would refuse at start anyway. Per version the page shows a live tool check and a "missing in Galaxy" state for a stored workflow deleted on the Galaxy side; the stored `revision_uuid` is compared there and never at analysis start, since Galaxy neither rewrites a revision nor reuses an id. Nothing is retired automatically: the administrator reads the badge and decides.
- **Snapshots.** Galaxy's display `name` and `annotation`, and the export kept in `definition`, are taken at publish and never refreshed. A rename in Galaxy does not reach users; if that ever matters it is a ticket of its own, not a return of the retagged concept.
- **A dependency on Galaxy internals.** The revision index is append-only and stable in Galaxy's source and has been for years, but it is behaviour, not a documented promise. `revision_uuid` is the guard.
- **ADR 0003 is unchanged.** Directories still name the two strings, `name_key` and `version_key` remain the identity, and the three rungs stay as they are.
- **Vocabulary.** *Publish* is the act of creating a version; *active* and *retired* are its two states; *Version* and *Revision* are rewritten in `CONTEXT.md`; *Retagged workflow* is removed; there is no *Lineage* entry because the name plays that role.
- **User-facing pages are unchanged**: a flat list of `name - version`, each with its run link. Revisit trigger: a lineage with too many active versions to read, which calls for a version picker on the run form.
- **Deferred, each with its trigger.** The compatibility diff, when an administrator first publishes a label without knowing what changed since the previous one, or if adoption is wanted after all. The run-form version picker, above. The lineage table, above.
- **Galaxy's side goes quieter.** An author looking at Galaxy alone cannot tell which revision GaaS publishes unless they keep the tags by hand. Acceptable because the author and the administrator are the same person today.
