## Overview

The Nuxt Galaxy server layer provides **secure, server-side API endpoints** for interacting with Galaxy and the database. It runs as Nitro server handlers and uses [Effect-TS](https://effect.website/) for type-safe error handling and dependency injection.

## Why a Server Layer?

### Security: Protect API Keys

Galaxy API keys must remain server-side:

```
┌─────────────────┐     ❌ Never exposed     ┌──────────────────┐
│  Nuxt Client    │                         │  Galaxy API      │
│                 │ ◀──── API Key stays ─── │  (External)      │
│ useFetch()      │     on server only      │  Rate limited    │
└─────────────────┘                         └──────────────────┘
        │                                              ▲
        │ HTTP                                         │ API Key
        ▼                                              │
┌─────────────────┐     ┌──────────────────┐     ┌────┴─────────────┐
│  Nitro Server   │────▶│  Effect.run      │────▶│  Galaxy API      │
│                 │     │  GalaxyFetch     │     │  (with key)      │
│  /api/galaxy/*  │     │                  │     │                  │
└─────────────────┘     └──────────────────┘     └──────────────────┘
```

The Galaxy API key (`GALAXY_API_KEY`) is stored in **server-side runtime config** and never reaches the browser.

### Data Synchronization

Server plugins handle background sync operations:
- **Analysis status updates** — Poll Galaxy for running analysis status
- **Dataset cache invalidation** — Clear cached data when workflows complete
- **Realtime subscriptions** — Push postgres_changes events to clients

### Type-Safe Error Handling

Server handlers use Effect-TS instead of try/catch:

```typescript
// Instead of fragile try/catch
export default defineEventHandler(async () => {
  try {
    return await fetchGalaxyWorkflows()
  }
  catch (e) {
    // What type is e? Who knows?
  }
})

// Use Effect for explicit error types
export default defineEventHandler(async () => {
  return getWorkflowsEffect().pipe(
    toGalaxyServiceUnavailable, // Map errors to HTTP 503
    Effect.provide(useGalaxyLayer()), // Inject Galaxy config
    Effect.runPromise,
  )
})
```

## Server Architecture

### Directory Structure

```
src/runtime/server/
├── api/
│   ├── galaxy/
│   │   ├── workflows.get.ts       # List available workflows
│   │   ├── tools/
│   │   │   └── [toolId].get.ts  # Get tool description
│   │   └── ...
│   ├── db/
│   │   ├── analyses.get.ts        # List analyses
│   │   ├── analyses.post.ts       # Create analysis
│   │   └── workflows.post.ts     # Create workflow
│   └── probe.get.ts              # Health check
├── plugins/
│   ├── galaxy.server.ts          # Validate module config
│   └── migrations.server.ts      # Optional: run migrations on boot
├── db/
│   ├── schema/                    # Drizzle schema definitions
│   └── migrations/                # Migration files
├── lib/
│   ├── migrate.ts                # Programmatic migration runner
│   └── seed.ts                   # Programmatic seed runner
└── utils/
    ├── galaxy.ts                  # Galaxy API utilities
    ├── drizzle.ts                 # Database connection
    └── grizzle/
        └── supabase.ts            # Server-side Supabase layers
```

### Server Plugins

**`galaxy.server.ts`** — Runs on every request
- Validates `GALAXY_URL` and `GALAXY_API_KEY` are configured
- Provides typed error if configuration is missing

**`migrations.server.ts`** — Runs on startup (optional)
- Only loaded if `galaxy: { runMigrations: true }` in `nuxt.config.ts`
- Applies pending Drizzle migrations automatically
- Useful for containerized deployments

```typescript [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['nuxt-galaxy'],
  galaxy: {
    runMigrations: true, // Enables migrations.server.ts
  }
})
```

| Endpoint | Method | Description |
|----------|--------|-------------|
| `/api/galaxy/workflows` | GET | List available workflows |
| `/api/galaxy/workflows/:id` | GET | Get workflow by ID |
| `/api/galaxy/tools/:id/:version` | GET | Get tool description |
| `/api/galaxy/histories` | GET | List user's histories |
| `/api/galaxy/instance` | GET | Galaxy instance info |
| `/api/galaxy/health` | GET | Galaxy connectivity check |

#### Database CRUD Endpoints

| Endpoint | Methods | Description |
|----------|---------|-------------|
| `/api/db/analyses` | GET, POST | List or create analyses |
| `/api/db/analyses/:id` | GET, DELETE | Get or delete analysis |
| `/api/db/workflows` | POST | Create workflow |
| `/api/db/datasets` | GET, POST | Dataset management |

## Effect-TS on the Server

Nuxt Galaxy uses Effect-TS for dependency injection and error handling on the server.

### Server Layers

```typescript
import { ServerSupabaseClient } from '#imports'
// In a server handler
import { Effect } from 'effect'

export default defineEventHandler(async (event) => {
  const program = Effect.gen(function* () {
    // Dependencies are injected from context
    const supabase = yield* ServerSupabaseClient
    const config = useRuntimeConfig(event)

    const { data } = yield* Effect.promise(
      () => supabase.from('analyses').select('*')
    )

    return data
  })

  return program.pipe(
    Effect.provide(ServerSupabaseClient.Live(event)),
    Effect.runPromise,
  )
})
```

### Available Server Layers

| Layer | Provides | Usage |
|-------|----------|-------|
| `ServerSupabaseClient.Live(event)` | Typed Supabase client | Database queries |
| `ServerSupabaseClaims.Live(event)` | Auth user claims (role, etc.) | Authorization |
| `GalaxyFetch.Live` | Galaxy API client | External Galaxy calls |
| `DatabaseLayer` | Drizzle ORM instance | Direct SQL operations |

### Error Mapping

Effect errors are mapped to HTTP responses:

| Effect Error | HTTP Response |
|--------------|---------------|
| `GalaxyServiceUnavailable` | 503 Service Unavailable |
| `AuthenticationError` | 401 Unauthorized |
| `AuthorizationError` | 403 Forbidden |
| `NotFoundError` | 404 Not Found |
| `DatabaseError` | 500 Internal Server Error |

## Supabase on the Server

### Server-Side Client

Server handlers use `serverSupabaseClient` from `@nuxtjs/supabase`:

```typescript
import { serverSupabaseClient } from '#supabase/server'

export default defineEventHandler(async (event) => {
  const supabase = await serverSupabaseClient<Database>(event)
  const { data, error } = await supabase
    .from('analyses')
    .select('*')
    .eq('owner_id', userId)

  if (error)
    throw createError({ statusCode: 500, message: error.message })
  return data
})
```

### RLS in Server Context

When using `serverSupabaseClient`, RLS policies apply just like on the client:

```typescript
// This respects the RLS policy: owner_id = auth.uid()
const { data } = await supabase
  .from('analyses')
  .select('*')

// To bypass RLS (e.g., admin operations), use the service role client
const serviceClient = createClient(
  process.env.SUPABASE_URL,
  process.env.SUPABASE_SERVICE_KEY
)
```

::warning
The service role key bypasses all RLS policies. Only use it in trusted server contexts, never expose it to clients.
::

## File Storage

### Upload Flow

1. Client calls `useUploadFileToStorage()` composable
2. File uploads to Supabase Storage (analysis_files bucket)
3. Server inserts record into `galaxy.uploaded_datasets`
4. RLS ensures user can only access their own uploads

### Signed URLs

For secure file access, server generates time-limited signed URLs:

```typescript
export default defineEventHandler(async (event) => {
  const storage = useRuntimeConfig(event).supabase.storage
  const { data, error } = await storage
    .from('analysis_files')
    .createSignedUrl(path, 3600) // 1 hour expiry

  return { url: data?.signedUrl }
})
```

## Health Check

The `/api/probe` endpoint checks:
- Galaxy API connectivity
- Supabase database connectivity
- Required environment variables

Use it for:
- Docker health checks
- Kubernetes liveness/readiness probes
- Deployment verification

## Environment Variables

| Variable | Used By | Description |
|----------|---------|-------------|
| `GALAXY_URL` | Server | Galaxy API endpoint |
| `GALAXY_API_KEY` | Server | Galaxy API key (server-only) |
| `GALAXY_DRIZZLE_DATABASE_URL` | Server | PostgreSQL connection |
| `SUPABASE_URL` | Client + Server | Supabase API endpoint |
| `SUPABASE_KEY` | Client | Supabase anon key |
| `SUPABASE_SERVICE_KEY` | Server | Service role key (for storage) |
