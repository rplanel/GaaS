## Overview

The Nuxt Galaxy server layer provides **secure, server-side API endpoints** for interacting with Galaxy and the database. It runs as Nitro server handlers and uses [Effect-TS](https://effect.website/) for type-safe error handling and dependency injection.

## Why a Server Layer?

### Security: Protect API Keys

Galaxy API keys must remain server-side:

```
┌─────────────────┐     ❌ Never exposed     ┌──────────────────┐
│  Nuxt Client    │                         │  Galaxy API      │
│                 │ ◀──── API Key stays ─── │  (External)      │
│ useFetch()      │     on server only      │  Rate limited    │
└─────────────────┘                         └──────────────────┘
        │                                              ▲
        │ HTTP                                         │ API Key
        ▼                                              │
┌─────────────────┐     ┌──────────────────┐     ┌────┴─────────────┐
│  Nitro Server   │────▶│  Effect.run      │────▶│  Galaxy API      │
│                 │     │  GalaxyFetch     │     │  (with key)      │
│  /api/galaxy/*  │     │                  │     │                  │
└─────────────────┘     └──────────────────┘     └──────────────────┘
```

The Galaxy API key (`GALAXY_API_KEY`) is stored in **server-side runtime config** and never reaches the browser.

### Data Synchronization

Server plugins handle background sync operations:
- **Analysis status updates** — Poll Galaxy for running analysis status
- **Dataset cache invalidation** — Clear cached data when workflows complete
- **Realtime subscriptions** — Push postgres_changes events to clients

### Type-Safe Error Handling

Server handlers use Effect-TS instead of try/catch:

```typescript
// Instead of fragile try/catch
export default defineEventHandler(async () => {
  try {
    return await fetchGalaxyWorkflows()
  }
  catch (e) {
    // What type is e? Who knows?
  }
})

// Use Effect for explicit error types
export default defineEventHandler(async () => {
  return getWorkflowsEffect().pipe(
    toGalaxyServiceUnavailable, // Map errors to HTTP 503
    Effect.provide(useGalaxyLayer()), // Inject Galaxy config
    Effect.runPromise,
  )
})
```

```

├── api/
│   ├── galaxy/
│   │   ├── workflows.get.ts       # List available workflows
│   │   ├── tools/
│   │   │   └── [toolId].get.ts  # Get tool description
│   │   └── ...
│   ├── db/
│   │   ├── analyses.get.ts        # List analyses
│   │   ├── analyses.post.ts       # Create analysis
│   │   └── workflows.post.ts     # Publish a version
│   └── probe.get.ts              # Health check
├── plugins/
│   ├── galaxy.server.ts          # Validate module config
│   └── migrations.server.ts      # Optional: run migrations on boot
├── db/
│   ├── schema/                    # Drizzle schema definitions
│   └── migrations/                # Migration files
├── lib/
│   ├── migrate.ts                # Programmatic migration runner
│   └── seed.ts                   # Programmatic seed runner
└── utils/
    ├── galaxy.ts                  # Galaxy API utilities
    ├── drizzle.ts                 # Database connection
    └── grizzle/
        └── supabase.ts            # Server-side Supabase layers
```

### Server Plugins

**`galaxy.server.ts`** — Runs on every request
- Validates `GALAXY_URL` and `GALAXY_API_KEY` are configured
- Provides typed error if configuration is missing

**`migrations.server.ts`** — Runs on startup (optional)
- Only loaded if `galaxy: { runMigrations: true }` in `nuxt.config.ts`
- Applies pending Drizzle migrations automatically
- Useful for containerized deployments

```typescript [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['nuxt-galaxy'],
  galaxy: {
    runMigrations: true, // Enables migrations.server.ts
  }
})
```

## Starting an Analysis

`POST /api/db/analyses` starts one analysis: it uploads the datasets the request names into the analysis on Galaxy, asks Galaxy to start the workflow with them, and records the analysis with its inputs. The UI layer calls it from the workflow form, but the form is not the only client, so what the endpoint accepts and what it refuses are written here rather than left to be read off the form.

### Request Body

A JSON object. `AnalysisBody`, exported from `nuxt-galaxy`, is inferred from the schema the endpoint checks the body against, so a body that type accepts is one the endpoint accepts.

```json
{
  "name": "My RNA-Seq analysis",
  "workflowId": 1,
  "datamap": {
    "0": { "storage_object_id": "3f1c2a0e-…" },
    "1": { "storage_object_id": "9b7d4e11-…" }
  },
  "parameters": {}
}
```

| Field | Accepts | Rule |
|-------|---------|------|
| `name` | string | At most 256 characters as sent (the column is `varchar(256)`), and not only whitespace. Stored as typed, not trimmed |
| `workflowId` | number | The identifier of a published version. Not coerced: `"1"` is refused, because the form sends a number and a client sending a string has a bug worth hearing about |
| `datamap` | object | One entry per dataset input the workflow declares, keyed by the step's index in the workflow, each carrying the `storage_object_id` of an uploaded dataset. Other keys on an entry are kept as sent: the form sends the whole uploaded-dataset row, and copying an analysis later reads the stored datamap back |
| `parameters` | object, optional | Values for the workflow's parameters, keyed as Galaxy expects them (`GalaxyWorkflowParameters` in `blendtype`). Passed on unread; absent means none |

Unknown top-level keys are ignored rather than refused, so an additive client change is not a `400`.

### Order of the Checks

Every refusal below happens **before anything is created**, on Galaxy or in the database, so a request nobody can act on costs a round trip and nothing more. The checks happen in this order, and the first to fail answers:

1. **Body shape.** The body is read with its parse failure caught, so an unparseable body is this endpoint's own `400` rather than h3's `Bad Request`. A body that is not the shape above is refused with a sentence naming the field.
2. **Session.** No signed-in user is `401`.
3. **Galaxy health.** Galaxy down or under maintenance is `503`.
4. **The workflow.** `workflowId` has to name a workflow the caller may start, or the answer is `404`.
5. **The version is active.** A retired version (ADR 0004) is `409`, with a sentence naming the version. The users' list hides retired versions, so only a client holding a stale id reaches this.
6. **The datamap against the workflow.** The workflow's stored definition says which dataset inputs it declares. A datamap that leaves a required one out, or names a step that takes no dataset, is `400`. This is the refusal whose sentence the form shows the reader word for word, since it names the field to go back to.
7. **Preparing the analysis on Galaxy.** Only now is anything created. If Galaxy accepts the request and gives nothing back to start against, the answer is `503`, and nothing is left behind.

A failure after that point, an upload Galaxy refuses or a start it will not accept, is a `500`, and the analysis prepared for it is taken back out, so nothing is left behind there either.

Because the body is checked first, a `400` never implies the caller was authenticated. Because the workflow is resolved before the datamap is compared with it, a `404` says nothing about the datamap: there is no definition to compare it against.

### Error Responses

| Status | When | Message |
|--------|------|---------|
| 400 | The body is missing, unparseable, or not the shape above | One of the five sentences below, naming the field |
| 400 | The datamap cannot start the workflow it names | Names the input by its label, see below |
| 401 | No signed-in user | `Unauthorized` |
| 404 | `workflowId` names no workflow the caller may start | `No workflow 7 is available` |
| 409 | `workflowId` names a retired version (ADR 0004) | `Version "0.11" of "satelliteFinder" is retired; no analysis can be started on it.` |
| 503 | Galaxy is unavailable or under maintenance | `Galaxy is currently unavailable`, or `Galaxy is under maintenance: …` with Galaxy's own notice |
| 503 | A call to Galaxy answered 503, or Galaxy could not be reached | `Galaxy service is unavailable` |
| 503 | Galaxy did not prepare the analysis | `The analysis could not be prepared on Galaxy` |
| 500 | Anything else: a failure after the analysis was prepared (taken back out), or a deployment whose Galaxy service account has no row | `Internal Server Error`; the cause goes to the log, not to the caller |

::note
The message travels as the response's `statusMessage`, both in the status line and in the JSON body. Read it from the body: HTTP/2 carries no reason phrase, and over HTTP/1.1 Node fills in the status's default one when the server set none.
::

The `400` messages for the body, as they actually read. Only the first problem is answered, one sentence per round trip:

- `` The request body must be a JSON object carrying `name`, `workflowId` and `datamap` `` — no body, a body that could not be parsed, or one that is not an object
- `` `name` must be a non-empty string of at most 256 characters ``
- `` `workflowId` must be a number ``
- `` `datamap` must be an object whose entries each carry a `storage_object_id` `` — also the answer to `"datamap": "f"` and to an entry that is `null`
- `` `parameters` must be an object when present ``

The `400` messages for the datamap name each input by the label the workflow gives it, which is the word the form shows beside the field:

- `No dataset was provided for the input "Input FASTQ"` — a required input left out. Several read `for the inputs "Input FASTQ", "Input reference"`. An input the workflow never labelled is named `at step 3`.
- `This workflow declares no dataset input at step 7` — an entry for a step that takes no dataset, such as a parameter. Refused although Galaxy would ignore it: every datamap entry is uploaded before Galaxy sees the request, so an extra one would buy a dataset nothing uses.
- Both at once are one sentence, joined with a semicolon: `No dataset was provided for the input "Input reference"; this workflow declares no dataset input at step 7`.

An optional input may be left out. A workflow that declares no dataset inputs accepts an empty datamap. A workflow whose stored definition cannot be read is not compared with the datamap at all: the endpoint only refuses on what it knows.

### Response

`200` with the analysis's identifier and the identifiers of its input records:

```json
{ "id": 42, "inputIds": [7, 8] }
```

The UI layer navigates to `/analyses/42` on it.

## Publishing a Version

`POST /api/db/workflows` publishes one version: it labels one revision of a Galaxy stored workflow for the web application, the revision the body names or the latest when it names none, and nothing is copied in Galaxy (ADR 0004). The admin workflows page calls it from its publish dialog, but the dialog is not the only client, so what the endpoint accepts and what it refuses are written here rather than left to be read off the dialog.

### Request Body

A JSON object. `PublishVersionBody`, exported from `nuxt-galaxy`, is inferred from the schema the endpoint checks the body against, so a body that type accepts is one the endpoint accepts.

```json
{
  "galaxyId": "5e53d5d031d847c5",
  "name": "satelliteFinder",
  "label": "0.11",
  "revision": 3
}
```

| Field | Accepts | Rule |
|-------|---------|------|
| `galaxyId` | string | The Galaxy identifier of the stored workflow, as `GET /api/galaxy/workflows` lists it. Not blank |
| `name` | string | The name of the workflow to users, which every version of this stored workflow shares. At most 255 characters, and a legal results view directory name: letters, digits, dots, hyphens and underscores, starting with a letter or digit (ADR 0003). Stored as typed, case included |
| `label` | string | The version label users see beside the name. Same length and directory rule as `name`. Stored as typed |
| `revision` | integer, optional | The revision to publish, by the 0-based index `GET /api/galaxy/workflows/:id/versions` lists it under. A non-negative integer. Left out, the latest revision is published |

Unknown top-level keys are ignored rather than refused, so an additive client change is not a `400`.

The revision is the one the body names, or the latest one Galaxy holds for the stored workflow when it names none: the endpoint exports that revision and reads the revision index, the revision uuid and the snapshot off the export, so the three cannot disagree. Labels are not ordered, so an older revision can be published after a newer one; the publish dialog lists the revisions with their index, save time and step count, selects the latest by default, and shows the ones already published disabled with their label. The dialog always sends the revision it shows selected, the latest included, so the row pins what was on screen even when Galaxy gained a revision meanwhile; a client that leaves the field out gets the latest at the time of the request. Two numberings meet here: Galaxy's editor labels a revision from 1, while the API, the export, the download and the invocation carry the 0-based index. `revision` in the body and in every response is the index; every sentence an administrator reads, in the dialog and in the refusals below, shows the editor's number, index + 1, so the API's revision 3 reads "Revision 4".

### Order of the Checks

Every refusal below happens **before anything is written**, so a request nobody can act on costs a round trip and nothing more. The checks happen in this order, and the first to fail answers:

1. **Body shape.** The body is read with its parse failure caught, so an unparseable body is this endpoint's own `400` rather than h3's `Bad Request`. A body that is not the shape above, or whose `name` or `label` cannot name a results view directory, is refused with a sentence naming the field.
2. **Session.** No signed-in user is `401`.
3. **The export.** The named revision, or the latest, is exported from Galaxy. A revision Galaxy has no such index for, or a stored workflow Galaxy no longer has, is `404` with a sentence saying which. Galaxy down or answering 503 is `503`; an export that is not what it claims to be, such as a revision index that is not an integer of at least 0, or an export of another revision than the one asked for, is a fault (`500`).
4. **The label.** `name` and `label` together name a results view directory, so the pair is unique across the application, whichever stored workflow carries the name. A pair already published is `409`.
5. **The revision.** One revision of a stored workflow carries at most one label, since labels are immutable. A revision already published is `409`, naming the label it has.
6. **The name.** A stored workflow keeps one name once it has a version: the name is the lineage. A name that differs from it is `409`. The dialog locks the field, so this refuses only a client that did not.
7. **The tools.** Galaxy refuses to run a revision whose tools are not installed at their exact pinned version (`require_exact_tool_versions`), so publishing is a reviewed act: each distinct tool the revision pins is looked up in Galaxy at its pinned version, and a revision with any tool missing is `409`, naming the tools and their versions. Galaxy holds a tool at another version than the one asked for as readily as it holds none, so a lookup that answers with another version counts as missing too. Galaxy being unwell during a lookup is `503`, never a tool wrongly called missing. Checked after the label, the revision and the name, so a refusal fixed by retyping never costs the Galaxy round trips.
8. **Permission.** The insert goes through the caller's own session, so the database decides who may publish (the `workflows.insert` permission). A refusal is `403`, and it is the last check: nothing was written.

Because the body is checked first, a `400` never implies the caller was authenticated. Because the label is checked before the revision, a `409` about a label says nothing about whether the revision is published; the dialog shows one sentence at a time, and the administrator fixes them in the order they are read. Because the tools are checked last before the insert, a `409` about them says the label, the revision and the name were all accepted.

### Error Responses

| Status | When | Message |
|--------|------|---------|
| 400 | The body is missing, unparseable, or not the shape above | One of the sentences below, naming the field |
| 401 | No signed-in user | `Unauthorized` |
| 403 | The database refused the insert | `Permission denied` |
| 404 | The body named a revision Galaxy has no such index for (here `999`) | `Galaxy has no revision 1000 of stored workflow 5e53d5d031d847c5.` |
| 404 | Galaxy no longer has the stored workflow | `Galaxy no longer has stored workflow 5e53d5d031d847c5.` |
| 409 | The label is already used for this name | `Version "0.11" of "satelliteFinder" already exists.` |
| 409 | The revision is already published for this stored workflow (here index 3) | `Revision 4 is already published as version "0.10" of "satelliteFinder".` |
| 409 | The name differs from the one this stored workflow already carries | `This workflow is published as "satelliteFinder"; a new version keeps that name.` |
| 409 | A version was published between the checks and the insert, so a unique constraint refused it | `Another version was published meanwhile. Reload the page and try again.` |
| 409 | Galaxy does not hold every tool of the revision at its pinned version (here index 3) | `Revision 4 of "Satellite Finder" uses tools missing in Galaxy at their pinned version: toolshed.g2.bx.psu.edu/repos/iuc/bar/bar/2.0 2.0. Install them or choose another revision.` |
| 503 | A call to Galaxy answered 503, or Galaxy could not be reached, the export or a tool lookup included | `Galaxy service is unavailable` |
| 500 | Anything else: an export that is not a Galaxy export, a tool lookup Galaxy answered with a fault, a deployment whose Galaxy service account has no row, or a database fault | `Internal Server Error`; the cause goes to the log, not to the caller |

::note
The message travels as the response's `statusMessage`, both in the status line and in the JSON body. Read it from the body: HTTP/2 carries no reason phrase, and over HTTP/1.1 Node fills in the status's default one when the server set none.
::

The `400` messages, as they actually read. Only the first problem is answered, one sentence per round trip:

- `` The request body must be a JSON object carrying `galaxyId`, `name` and `label` `` — no body, a body that could not be parsed, or one that is not an object
- `` `galaxyId` must be a non-empty string ``
- `` `name` must be a non-empty string of at most 255 characters ``
- `` `label` must be a non-empty string of at most 255 characters ``
- `` `revision` must be a non-negative integer `` — a negative index, a fraction, a numeric string or `null`; leave the field out to publish the latest
- `` `name` cannot name a results view directory. Use letters, digits, dots, hyphens and underscores, starting with a letter or digit. `` — and the same sentence for `` `label` ``

The publish dialog shows every `4xx`'s sentence to the administrator as written, next to the fields; only `401`, `403` and `503` get their own wording there, since a bare `Unauthorized` or `Permission denied` would mislead.

The dialog also runs the tools check itself, for the revision it has selected, through `GET /api/galaxy/workflows/:id/revisions/:revision/tools`. That proxy exports the revision and looks each distinct tool up at its pinned version, and answers `{ "missing": [{ "toolId": "…", "toolVersion": "…" }], "checked": 4 }` in the same `{ data, error }` envelope as the revisions proxy; a `revision` that is not a non-negative integer is `400` before Galaxy is asked. Under the revision picker the dialog says either that all the tools are installed at their pinned version, or names the missing ones, or that they could not be checked. **Publish** is disabled while the check is in flight, while any tool is missing and when the check failed, so the server's `409` above is reached only by another client, or by a tool removed between the check and the click; the dialog shows that sentence as written too. Galaxy keeps old tool versions installed unless an administrator removes them, so this rarely fires; when it does, the administrator reads which tools before anything is written.

### Response

`200` with the version row as it was written: the stored workflow, the revision by index and by uuid, the name and the label, the export as `definition`, who published and when, and `active`, which is `true` for a version just published.

```json
{
  "id": 5,
  "galaxy_id": "5e53d5d031d847c5",
  "name": "Satellite Finder",
  "name_key": "satelliteFinder",
  "version_key": "0.11",
  "revision": 3,
  "revision_uuid": "fa95ecd4-ed11-49e2-b3d6-8f178b807256",
  "definition": { "a_galaxy_workflow": true, "...": "..." },
  "user_id": 1,
  "published_at": "2026-09-24T09:12:03.412+00:00",
  "published_by": "1f2e3d4c-…",
  "active": true,
  "annotation": null
}
```

The admin workflows page adds the version to the stored workflow's row and tells the administrator; users find it in the workflows list and start an analysis that runs that revision.

## Retiring a Version

`PATCH /api/db/workflows/:workflowId` retires one version, or makes a retired one active again (ADR 0004). *Active* means startable by users and nothing else: a retired version leaves the users' workflows list and the sidebar, and starting an analysis on it is refused; everything it already has, its analyses, their results views and its usage statistics, is untouched. Nothing is asked of Galaxy. The admin workflows page calls it from the **Active** switch beside each version, but the switch is not the only client, so what the endpoint accepts and what it refuses are written here.

`:workflowId` is the version row's `id`, the one the workflows list serves and an analysis references. `active` is the only column of a version an update may touch, and this is the one endpoint that touches it.

### Request Body

A JSON object. `VersionActiveBody`, exported from `nuxt-galaxy`, is inferred from the schema the endpoint checks the body against.

```json
{
  "active": false
}
```

| Field | Accepts | Rule |
|-------|---------|------|
| `active` | boolean | `false` retires the version, `true` makes it active again. Not coerced: the string `"false"` is refused |

Unknown top-level keys are ignored rather than refused, so an additive client change is not a `400`.

### Order of the Checks

Every refusal below happens **before anything is written**. The checks happen in this order, and the first to fail answers:

1. **The path.** Anything but a non-negative integer in place of `:workflowId` names no version and is `404`, before the body is read.
2. **Body shape.** The body is read with its parse failure caught, so an unparseable body is this endpoint's own `400` rather than h3's `Bad Request`. A body that is not the shape above is refused with a sentence naming the field.
3. **Session.** No signed-in user is `401`.
4. **The version.** The id is looked up among the versions of the Galaxy service account; no row is `404`.
5. **Permission.** The update goes through the caller's own session, so the database decides who may retire: the `workflows.update` permission, which the seed gives the admin role, and the column-level grant that leaves `active` the only column an update may touch. A refusal is `403`, and it is the last check: nothing was written.

### Error Responses

| Status | When | Message |
|--------|------|---------|
| 400 | The body is missing, unparseable, or not the shape above | One of the two sentences below |
| 401 | No signed-in user | `Unauthorized` |
| 403 | The database refused the update | `Permission denied` |
| 404 | The path names no version | `No workflow 7 is available` |
| 500 | Anything else: a deployment whose Galaxy service account has no row, or a database fault | `Internal Server Error`; the cause goes to the log, not to the caller |

::note
The message travels as the response's `statusMessage`, both in the status line and in the JSON body. Read it from the body: HTTP/2 carries no reason phrase, and over HTTP/1.1 Node fills in the status's default one when the server set none.
::

The `400` messages, as they actually read:

- `` The request body must be a JSON object carrying `active` `` — no body, a body that could not be parsed, or one that is not an object
- `` `active` must be a boolean: false retires the version, true makes it active again ``

The Active switch shows every `4xx`'s sentence to the administrator in a toast, as written; only `401` and `403` get their own wording there, since a bare `Unauthorized` or `Permission denied` would mislead. The switch does not move until the server has said yes.

### Response

`200` with the version row as it was written, `active` as asked:

```json
{
  "id": 5,
  "galaxy_id": "5e53d5d031d847c5",
  "name": "Satellite Finder",
  "name_key": "satelliteFinder",
  "version_key": "0.11",
  "revision": 3,
  "revision_uuid": "fa95ecd4-ed11-49e2-b3d6-8f178b807256",
  "definition": { "a_galaxy_workflow": true, "...": "..." },
  "user_id": 1,
  "published_at": "2026-09-24T09:12:03.412+00:00",
  "published_by": "1f2e3d4c-…",
  "active": false,
  "annotation": null
}
```

From then on users no longer find the version in the workflows list or the sidebar, and `POST /api/db/analyses` answers `409` for it, with `Version "0.11" of "satelliteFinder" is retired; no analysis can be started on it.` Its past analyses keep their pages, their results views and their usage statistics: hiding happens in the users' list query, never in a select policy, so a past analysis still resolves the version it ran. Sending `true` restores everything.

## Deleting a Version

`DELETE /api/db/workflows/:workflowId` deletes one version, for the mistaken publish: a wrong label or a wrong revision (ADR 0004). It is allowed only while no analysis references the version; otherwise the database refuses and the administrator reads that the version has analyses and can be retired instead. Once the row is gone, its revision can be published again under another label, since the unique on the revision was what refused a second one. Nothing is asked of Galaxy. The admin workflows page calls it from the **Delete** control beside each version, after a confirmation naming the version, but the page is not the only client, so what the endpoint refuses is written here.

`:workflowId` is the version row's `id`, the one the workflows list serves and an analysis references. The request has no body.

### Order of the Checks

Every refusal below happens **before anything is deleted**. The checks happen in this order, and the first to fail answers:

1. **The path.** Anything but a non-negative integer in place of `:workflowId` names no version and is `404`.
2. **Session.** No signed-in user is `401`.
3. **The version.** The id is looked up among the versions of the Galaxy service account; no row is `404`.
4. **Permission.** The delete goes through the caller's own session, so the database decides who may delete: the `workflows.delete` permission, which the seed gives the admin role. A refusal is `403`.
5. **The analyses.** `analyses.workflow_id` references the version with no `ON DELETE` clause, so Postgres refuses the delete of a version an analysis references. That refusal is `409`, with a sentence naming the version and pointing at retiring. It is the last check, and it is the database's: nothing was deleted.

A tag association from before ADR 0004 does not stand in the way: `workflows_to_tags` goes with the version.

### Error Responses

| Status | When | Message |
|--------|------|---------|
| 401 | No signed-in user | `Unauthorized` |
| 403 | The database refused the delete | `Permission denied` |
| 404 | The path names no version | `No workflow 7 is available` |
| 409 | An analysis references the version | `Version "0.11" of "satelliteFinder" has analyses and cannot be deleted; retire it instead.` |
| 500 | Anything else: a deployment whose Galaxy service account has no row, or a database fault | `Internal Server Error`; the cause goes to the log, not to the caller |

::note
The message travels as the response's `statusMessage`, both in the status line and in the JSON body. Read it from the body: HTTP/2 carries no reason phrase, and over HTTP/1.1 Node fills in the status's default one when the server set none.
::

The confirmation dialog shows every `4xx`'s sentence to the administrator as written, and stays open on it; only `401` and `403` get their own wording there, since a bare `Unauthorized` or `Permission denied` would mislead. Nothing closes until the server has said yes.

### Response

`200` with the version row that is gone:

```json
{
  "id": 5,
  "galaxy_id": "5e53d5d031d847c5",
  "name": "Satellite Finder",
  "name_key": "satelliteFinder",
  "version_key": "0.11",
  "revision": 3,
  "revision_uuid": "fa95ecd4-ed11-49e2-b3d6-8f178b807256",
  "definition": { "a_galaxy_workflow": true, "...": "..." },
  "user_id": 1,
  "published_at": "2026-09-24T09:12:03.412+00:00",
```

From then on the version is listed nowhere, and `POST /api/db/workflows` accepts the same revision (index 3) of that stored workflow again, under another label. Usage statistics are history over monitoring records and never referenced the row, so nothing there changes.

## Reading a Version's State

`GET /api/db/workflows/:workflowId/state` reads the **state of a version** (ADR 0004): whether it can still run, read live from Galaxy at the moment of the request. Four readings: **runnable**; **tools missing**, naming the tools Galaxy does not hold at their pinned version; **missing in Galaxy**, when the stored workflow no longer exists there; **revision mismatch**, when the revision Galaxy holds at the pinned index is not the one the version pinned, or the index names no revision any more. The reading writes nothing, and nothing is retired from it: the administrator reads it and decides, retiring being the remedy. The admin workflows page asks it once per version it lists and shows the answer as a badge beside the version, with a button to read it again; the page never fans out one request per tool, the fan-out to Galaxy happens here, four lookups at a time.

`:workflowId` is the version row's `id`. The request has no body.

### Order of the Checks

The checks happen in this order, and the first to decide answers:

1. **The path.** Anything but a non-negative integer in place of `:workflowId` names no version and is `404`.
2. **Session.** No signed-in user is `401`.
3. **The version.** The id is looked up among the versions of the Galaxy service account; no row is `404`.
4. **The stored workflow.** `GET api/workflows/{id}` on Galaxy. Galaxy deletes softly: a deleted stored workflow is left out of the list but is still described, `deleted: true`. A `404` or `400` from Galaxy, or a description that says `deleted`, reads **missing in Galaxy**, and nothing further is asked.
5. **The revision.** The pinned revision is exported by its index. A `400` from Galaxy means the index names no revision any more (the history was shortened); an export whose `uuid` is not the one the version pinned means another revision sits at that index (the history was rewritten). Both read **revision mismatch**, the second carrying Galaxy's uuid, and no tool is asked about. This is the one place the stored `revision_uuid` is compared, never at analysis start.
6. **The tools.** Each distinct tool of the exported revision is looked up at its pinned version, the check publishing runs. Any missing reads **tools missing**, naming them; none reads **runnable**.

Galaxy being unwell during any step is answered as such (`503`, or a logged `500`), never as a reading: a state the administrator might act on is only ever what Galaxy actually said.

### Error Responses

| Status | When | Message |
|--------|------|---------|
| 401 | No signed-in user | `Unauthorized` |
| 404 | The path names no version | `No workflow 7 is available` |
| 503 | A call to Galaxy answered 503, or Galaxy could not be reached | `Galaxy service is unavailable` |
| 500 | Anything else: a Galaxy read that failed for a reason of its own, a deployment whose Galaxy service account has no row, or a database fault | `Internal Server Error`; the cause goes to the log, not to the caller |

::note
The message travels as the response's `statusMessage`, both in the status line and in the JSON body. Read it from the body: HTTP/2 carries no reason phrase, and over HTTP/1.1 Node fills in the status's default one when the server set none.
::

The badge on the admin page says **not checked** for any of these, with the reason in its details; it never guesses a state from a failure.

### Response

`200` with one of four bodies, told apart by `state`:

```json
{ "state": "runnable" }
```

```json
{
  "state": "tools-missing",
  "missingTools": [
    { "toolId": "toolshed.g2.bx.psu.edu/repos/iuc/bar/bar/2.0", "toolVersion": "2.0" }
  ]
}
```

```json
{ "state": "missing-in-galaxy" }
```

```json
{ "state": "revision-mismatch", "galaxyRevisionUuid": "0b7c9a2e-1111-4222-8333-444455556666" }
```

`galaxyRevisionUuid` is absent when the index names no revision any more. `VersionState`, exported from `nuxt-galaxy`, is the union of the four.

On the admin page a stored workflow Galaxy no longer lists keeps a row for the versions published for it, named from the snapshot taken at publish and listed first, with no Publish button and with the Active switch and Delete still there: a version whose stored workflow vanished from Galaxy no longer drops out of the page silently, and retiring it is one click away. The list the page reads includes the stored workflows hidden in Galaxy's own list, marked as such beside their name, so only a deleted one is read as vanished.

## Usage Statistics Endpoints

Two endpoints answer **usage statistics** — aggregates over monitoring records — in one shape over two scopes:

| Endpoint | Method | Scope | Access |
|----------|--------|-------|--------|
| `/api/db/analyses/monitoring` | GET | Own usage — the analyses the signed-in user owns | Any signed-in user |
| `/api/db/analyses/monitoring/admin` | GET | Global usage — every user's analyses, in aggregate, with no per-user breakdown | `admin` role |

The UI layer draws them on the **Own usage** (`/profile/usage`) and **Global usage** (`/admin/usage`) pages, through the auto-imported `ownUsageStatisticsQuery` and `globalUsageStatisticsQuery` helpers.

```
GET /api/db/analyses/monitoring?from=2026-08-01&to=2026-08-31&granularity=day
GET /api/db/analyses/monitoring?granularity=month&workflowId=unknown
GET /api/db/analyses/monitoring/admin?from=2026-01-01&granularity=week
```

### Query Parameters

| Parameter | Accepts | Absent means |
|-----------|---------|--------------|
| `from` | `YYYY-MM-DD`, a UTC calendar day, inclusive | all time |
| `to` | `YYYY-MM-DD`, a UTC calendar day, inclusive | all time |
| `granularity` | `day`, `week`, `month` | `day` |
| `workflowId` | a positive integer, or `unknown` | all workflows |

- `to` is inclusive as a reader means it: `to=2026-08-31` includes the 31st.
- An **empty** value (`?from=`, `?to=`, `?granularity=`, `?workflowId=`) reads as absent, not as an error.
- `unknown` names the **Unknown workflow** bucket, which travels as a word because it has no identifier of its own.

::note
The Unknown workflow selection is subtler than "records whose workflow name is null". Per-workflow usage groups by workflow and takes `max(workflow_name)`, which is null only when **every** record in the group is nameless — so a workflow deleted halfway through its life keeps its name, and its later nameless records are counted inside its named entry. `workflowId=unknown` therefore selects records belonging to a workflow that carried no name **anywhere in the owner and range being asked about**, which is exactly the Unknown workflow entry a reader sees. One consequence: a workflow whose only named records fall outside the requested range appears as Unknown for that range.
::

### What Each Parameter Narrows

The response carries three dimensions: counts, per-workflow usage and the trend.

`from` and `to` narrow **all three**, so every dimension always covers the same analyses and they cannot disagree about which. The range filters on when an analysis *started*, never on when it finished, so one that ran for days belongs to the bucket it began in.

`workflowId` is a **workflow selection**, and it narrows **counts and the trend only**. It never narrows per-workflow usage, which is the list the selection is made from: a list that hid the entries a reader did not pick could not be the thing they pick from. It does reach the query that decides how far an all-time trend extends, so an all-time trend of one workflow spans that workflow's history rather than the deployment's.

`granularity` narrows nothing. It is how the trend groups the same analyses, not which ones are counted, so counts and per-workflow usage are identical at every bucket width and the trend still sums to them.

::warning
With a `workflowId` in force, **the per-workflow totals do not sum to the counts total** — per-workflow usage still covers every workflow in range. The invariant that holds at every granularity is that the **trend** totals sum to the counts total.
::

### Error Responses

| Status | When |
|--------|------|
| 400 | A parameter cannot be read |
| 401 | No signed-in user |
| 403 | Signed in without the `admin` role — admin endpoint only |
| 500 | The query failed |

Both endpoints read their parameters **before** authentication or the role check, so a malformed parameter costs a round trip and nothing else — and a `400` never implies the caller was authorised.

The messages as they actually read: the self endpoint answers `401 Unauthorized` and `500 Internal Server Error`; the admin endpoint answers `500 Internal Server Error`, but its `401` and `403` carry the underlying error's own text rather than a fixed string.

A `400` is the answer to:

- A malformed or unreal date. `2026-02-31` is refused, not rolled forward to 3 March, so a typo cannot quietly shift the range that was asked for.
- A reversed range, `from` falling after `to`.
- A range covering more than **3653 days** (ten years). Unbounded, `from=0001-01-01&to=9999-12-31` would ask the trend for millions of points. The cap measures `from` to `to`-or-today, so `?from=0001-01-01` alone is refused just as hard as a two-ended span. A range with only a `to` needs no cap: the span then begins at the earliest analysis, so the data bounds it.
- A `granularity` outside the three. A misspelt value is refused rather than quietly falling back to `day`, so nobody gets a chart they did not ask for.
- A `workflowId` that is neither plain digits nor the word `unknown`: `abc`, `-1`, `0`, `1.5`, `3,4`, `+3`, `%203` (a leading space), `0x10`, `1e3`, `007`, anything past `2147483647`, or the parameter repeated. `0` because identifiers are `serial` and start at 1; `007` because it is a second spelling of a number that already has one; `2147483647` itself is valid, and anything above it is refused because `workflow_id` is an `integer` column and nothing larger can be stored, let alone matched.

A well-formed identifier nobody recognises is **200 with zeroes**, not a 404: the endpoint cannot tell "deleted long ago" from "never existed" without a lookup the snapshot design avoids.

### Buckets and UTC

A **bucket** is one interval of the trend, aligned to **UTC calendar boundaries**: a day, an ISO week starting Monday, or a calendar month. Bucket keys as they travel:

| Granularity | Key | Notes |
|-------------|-----|-------|
| `day` | `YYYY-MM-DD` | The day itself |
| `week` | `YYYY-MM-DD` | The **Monday** of the ISO week |
| `month` | `YYYY-MM` | The calendar month |

Every bucket in the span is present and **zero-filled**: a quiet fortnight inside "last 30 days" still returns thirty points rather than collapsing onto the days that carry records. A requested range keeps its empty buckets; with no range, the data decides its own extent.

::note
**The first bucket key can fall before `from`.** At `granularity=week`, `?from=2026-08-30&to=2026-09-06` — a range starting on a Sunday — returns `2026-08-24` and `2026-08-31`, because each bucket is the ISO week *containing* a date and those weeks begin on the Monday. The same applies at `month`, where a range starting mid-August returns `2026-08`. It reads like an off-by-one and is not: it follows from aligning buckets to UTC calendar boundaries.
::

::warning
An all-time trend is bounded only by the data. The ten-year cap above protects a range that was asked for; it cannot protect one that was not. On a long-lived deployment, `granularity=day` with no range returns a point for every day between the first and the last analysis. The UI avoids this by choosing months for all time, but the endpoint will answer it, so a client asking for daily all-time buckets should expect a large response.
::

### Response Shape

Both endpoints return the same `AnalysisMonitoringStats`:

```typescript
interface AnalysisMonitoringCounts {
  total: number
  success: number
  error: number
  cancelled: number
  pending: number
}

interface AnalysisMonitoringStats extends AnalysisMonitoringCounts {
  successRate: number
  perWorkflow: AnalysisMonitoringWorkflowUsage[]
  trend: AnalysisMonitoringTrendPoint[]
}

interface AnalysisMonitoringWorkflowUsage extends AnalysisMonitoringCounts {
  workflowId: number | null
  name: string | null
  version: string | null
  successRate: number
}

interface AnalysisMonitoringTrendPoint extends AnalysisMonitoringCounts {
  bucket: string
  successRate: number
}
```

**The four outcomes.** Exactly one applies to every analysis, and the counts partition `total` between them. The wire names differ from the words a reader sees:

| Wire | Displayed | Meaning |
|------|-----------|---------|
| `success` | **Succeeded** | The Galaxy run reached a result |
| `error` | **Failed** | The Galaxy run ended in error — never "error" or "errored" in anything a user reads |
| `cancelled` | **Cancelled** | Stopped or deleted before reaching a result |
| `pending` | **Pending** | Still running |

**`successRate`** is the share of analyses with a definitive outcome that succeeded — `success / (success + error)` — with `pending` and `cancelled` excluded from the denominator. One formula computes it on every path: the overall rate, each per-workflow entry and each trend point.

::warning
`successRate` is `0` on the wire, **never `null`**. A workflow with nothing finished and a workflow where everything failed both carry `0`. The rule that a success rate *has no value until something has finished*, and is then shown as a dash rather than as zero, is one the API does not express: a consumer has to test `success + error === 0` for itself. The UI does exactly that. Without it, a client draws a zero rate for analyses that are merely still running.
::

**`perWorkflow`** is per-workflow usage: one entry per workflow version in range, each with its own counts and success rate. It has **no defined order** — the query groups and never sorts, so the order is whatever Postgres returns, with the Unknown workflow entry appended last. A consumer that wants "most used first" must sort; the UI does.

The Unknown workflow entry arrives as `workflowId: null`, `name: "unknown"`, `version: null`. `name` never actually reaches the wire as `null`, so **`workflowId` is the field to test.** And `"unknown"` is a wire value, not a label: the words a reader sees are "Unknown workflow".

`version` is `null` whenever the snapshot never captured one. That is not only the Unknown workflow — a **named** workflow can carry a null version too.

**`trend`** is the series, **ordered oldest bucket first and contiguous**, because it is built by walking the span rather than by reading rows back. Consecutive `bucket` keys differ by exactly one bucket at the granularity that was asked for. Unlike `perWorkflow`, no field on a trend point is nullable.

::note
The UI always sends `granularity`, even where it matches the endpoint default, because it works out a bucket width from the range and should say which one it drew. It sends `workflowId` only when a workflow is selected. The endpoint's default (`day`) and the interface's automatic granularity (worked out from the length of the range, and `month` for all time) differ on purpose, and both are correct.
::

## Effect-TS on the Server

Nuxt Galaxy uses Effect-TS for dependency injection and error handling on the server.

### Server Layers

```typescript
import { ServerSupabaseClient } from '#imports'
// In a server handler
import { Effect } from 'effect'

export default defineEventHandler(async (event) => {
  const program = Effect.gen(function* () {
    // Dependencies are injected from context
    const supabase = yield* ServerSupabaseClient
    const config = useRuntimeConfig(event)

    const { data } = yield* Effect.promise(
      () => supabase.from('analyses').select('*')
    )

    return data
  })

  return program.pipe(
    Effect.provide(ServerSupabaseClient.Live(event)),
    Effect.runPromise,
  )
})
```

### Available Server Layers

| Layer | Provides | Usage |
|-------|----------|-------|
| `ServerSupabaseClient.Live(event)` | Typed Supabase client | Database queries |
| `ServerSupabaseClaims.Live(event)` | Auth user claims (role, etc.) | Authorization |
| `GalaxyFetch.Live` | Galaxy API client | External Galaxy calls |
| `DatabaseLayer` | Drizzle ORM instance | Direct SQL operations |

### Error Mapping

Effect errors are mapped to HTTP responses:

## Supabase on the Server

### Server-Side Client

Server handlers use `serverSupabaseClient` from `@nuxtjs/supabase`:

```typescript
import { serverSupabaseClient } from '#supabase/server'

export default defineEventHandler(async (event) => {
  const supabase = await serverSupabaseClient<Database>(event)
  const { data, error } = await supabase
    .from('analyses')
    .select('*')
    .eq('owner_id', userId)

  if (error)
    throw createError({ statusCode: 500, message: error.message })
  return data
})
```

### RLS in Server Context

When using `serverSupabaseClient`, RLS policies apply just like on the client:

```typescript
// This respects the RLS policy: owner_id = auth.uid()
const { data } = await supabase
  .from('analyses')
  .select('*')

// To bypass RLS (e.g., admin operations), use the service role client
const serviceClient = createClient(
  process.env.SUPABASE_URL,
  process.env.SUPABASE_SERVICE_KEY
)
```

::warning
The service role key bypasses all RLS policies. Only use it in trusted server contexts, never expose it to clients.
::

```typescript
export default defineEventHandler(async (event) => {
```
