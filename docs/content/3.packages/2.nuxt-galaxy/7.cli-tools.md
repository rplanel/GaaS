## Overview

Nuxt Galaxy provides two CLI tools for production operations:

- **`nuxt-galaxy-migrate`** — Run database migrations
- **`nuxt-galaxy-seed`** — Seed database with initial data

Both tools are bundled with the published package and work without source code access.

## Installation

The CLI tools are included when you install `nuxt-galaxy`:

```bash
pnpm add nuxt-galaxy
```

They are available via `npx`:

```bash
npx nuxt-galaxy-migrate --help
npx nuxt-galaxy-seed --help
```

## Environment Variables

Both tools read `GALAXY_DRIZZLE_DATABASE_URL` from environment:

```bash [.env]
# Local development
GALAXY_DRIZZLE_DATABASE_URL="postgresql://postgres:postgres@127.0.0.1:54322/postgres"

# Supabase Cloud (via connection pooler)
GALAXY_DRIZZLE_DATABASE_URL="postgresql://postgres.[project-ref]:[password]@aws-0-[region].pooler.supabase.com:6543/postgres"
```

::warning
Never commit environment variables to version control. Use `.env.example` as a template.
::

## Database Migrations

### `nuxt-galaxy-migrate`

Run all pending database migrations bundled with the package.

```bash [Terminal]
# Basic usage (reads GALAXY_DRIZZLE_DATABASE_URL from env)
npx nuxt-galaxy-migrate

# Output:
# ✅ nuxt-galaxy: Database migrations applied successfully
```

### How It Works

1. Connects to PostgreSQL using `GALAXY_DRIZZLE_DATABASE_URL`
2. Scans `dist/runtime/server/db/migrations/` for `.sql` files
3. Applies pending migrations in chronological order
4. Tracks progress in `drizzle.__drizzle_migrations` table

### Migration Sources

Migrations can come from two places:

| Source | When Used |
|--------|-----------|
| `src/runtime/server/db/migrations/` (dev) | During development, testing migrations |
| `dist/runtime/server/db/migrations/` (bundled) | In production, installed via npm |

The CLI automatically resolves the correct path:

```typescript
function getMigrationsFolder(): string {
  // Works both in development (src/) and production (dist/)
  return resolve(currentDir, '..', 'db', 'migrations')
}
```

### Custom Table Names

For advanced use cases, customize the migrations tracking table:

```typescript
import { runMigrations } from 'nuxt-galaxy/migrate'

await runMigrations(databaseUrl, {
  migrationsTable: 'custom_migrations',
  migrationsSchema: 'my_schema'
})
```

| Option | Default | Description |
|--------|---------|-------------|
| `migrationsTable` | `__drizzle_migrations` | Table name for tracking |
| `migrationsSchema` | `drizzle` | Schema for tracking table |

### Running Migrations on Boot

Enable automatic migrations on server startup:

```typescript [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['nuxt-galaxy'],
  galaxy: {
    runMigrations: true // Enables migrations.server.ts plugin
  }
})
```

::warning
Only enable `runMigrations: true` for simple deployments. For production, run migrations explicitly before deploying to avoid race conditions.
::

## Database Seeding

### `nuxt-galaxy-seed`

Populate the database with initial data: Galaxy instances, users, and role permissions.

```bash [Terminal]
# Create a seed config file
cp node_modules/nuxt-galaxy/dist/runtime/server/db/seed.example.json seed.json

# Edit seed.json with your data
# Then run:
npx nuxt-galaxy-seed seed.json
```

### Seed Config Format

```json [seed.json]
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "instances": [
    {
      "url": "https://galaxy.example.org",
      "name": "My Galaxy Instance"
    }
  ],
  "users": [
    {
      "email": "admin@example.org",
      "instanceUrl": "https://galaxy.example.org"
    }
  ],
  "rolePermissions": [
    {
      "roleName": "admin",
      "permissions": [
        "workflows.insert",
        "workflows.update",
        "workflows.delete",
        "instances.insert",
        "instances.delete",
        "users.delete"
      ]
    },
    {
      "roleName": "user",
      "permissions": [
        "workflows.select",
        "instances.select"
      ]
    }
  ]
}
```

### Seed Config Fields

| Field | Required | Description |
|-------|----------|-------------|
| `instances` | Yes | Array of Galaxy instances to register |
| `users` | No | Users to pre-register (links to instances) |
| `rolePermissions` | No | Permission mappings for roles |

#### Instances

```json
{
  "url": "https://galaxy.example.org", // Required: valid URL
  "name": "My Galaxy Instance" // Required: display name
}
```

#### Users

```json
{
  "email": "user@example.org", // Required: valid email
  "instanceUrl": "https://galaxy.example.org" // Required: must match an instance URL
}
```

::note
Users seeded here are Galaxy-side references, not Supabase auth users. Supabase auth users are managed separately through the auth UI.
::

#### Role Permissions

```json
{
  "roleName": "admin", // Required: must exist in galaxy_rbac.roles
  "permissions": [ // Required: array of permission strings
    "workflows.insert", // Format: {resource}.{action}
    "workflows.delete"
  ]
}
```

### Dry Run

Preview changes without applying them:

```bash [Terminal]
npx nuxt-galaxy-seed seed.json --dry-run
```

Output shows what would be inserted:

```
📦 Seeding 1 instance(s)...
   ✅ Instance: My Galaxy Instance (https://galaxy.example.org)
👤 Seeding 1 user(s)...
   ✅ User: admin@example.org (My Galaxy Instance)
🔐 Seeding role permissions...
   ✅ Role 'admin': 5 permission(s)
🎉 Seeding completed successfully!

(Dry run - no changes applied)
```

### Idempotent Seeding

The seeder is safe to run multiple times:

- **Instances**: Uses `ON CONFLICT DO NOTHING` on unique `url` constraint
- **Users**: Uses `ON CONFLICT DO NOTHING` on unique `email` constraint
- **Role Permissions**: Uses `ON CONFLICT DO NOTHING` on `(role_id, permission)`

This means you can run the seed command multiple times without duplicates.

### Exit Codes

| Code | Meaning |
|------|---------|
| 0 | Success |
| 1 | General error |
| 2 | Validation error (invalid config) |
| 3 | Config error (file not found) |
| 4 | Database error |
| 5 | Reference error (missing instance/role) |

### Programmatic API

Use the seed runner programmatically in your code:

```typescript
import { runSeed, validateSeedConfig } from 'nuxt-galaxy/seed'

// Validate configuration
const config = validateSeedConfig(jsonData)

// Run seed
await runSeed(config, process.env.GALAXY_DRIZZLE_DATABASE_URL)
```

## Development Automation

### Creating Migrations

```bash [Terminal]
# After modifying Drizzle schema, generate migration
pnpm drizzle:generate

# Apply to local database
pnpm drizzle:migrate

# Generate TypeScript types from live DB
pnpm supabase:generate:types
```

### Full Galaxy Migration Suite

Create all Galaxy-specific migrations at once:

```bash [Terminal]
pnpm supabase:migration:galaxy:create
```

This runs sequentially:
1. `supabase:migration:new bucket` — Storage bucket setup
2. `drizzle:generate` — Generate SQL from schema
3. `supabase:migration:new galaxy` — Core schema
4. `supabase:migration:new realtime` — Realtime publication
5. `supabase:migration:new rbac` — Role-based access control
6. `supabase:migration:new rls` — Row level security

## Production Deployment Checklist

1. ✓ Set `GALAXY_DRIZZLE_DATABASE_URL` in production environment
2. ✓ Run migrations:
   ```bash
   npx nuxt-galaxy-migrate
   ```
3. ✓ Seed initial data (optional):
   ```bash
   npx nuxt-galaxy-seed seed.json
   ```
4. ✓ Verify health check: `/api/probe`
5. ✓ Deploy Nuxt application

## Troubleshooting

### "Failed to connect to database"

- Verify `GALAXY_DRIZZLE_DATABASE_URL` is set correctly
- Check database is accessible from the deployment environment
- For Supabase Cloud: ensure pooler URL is used (not direct connection)

### "No migrations to apply"

- Migrations are already up to date
- Check the `drizzle.__drizzle_migrations` table for applied migrations

### "Instance not found" (seeding)

- The `instanceUrl` in user seed must match an instance URL in instances array
- Seeding users requires instances to be seeded first (same transaction)

### "Role not found" (seeding)

- The `roleName` must exist in `galaxy_rbac.roles` table
- Run migrations first to create the RBAC schema
