## Why a database?

Nuxt Galaxy uses a database to extend Galaxy's capabilities without modifying the Galaxy instance itself. Using a local database provides:

- **Reduced API calls** — Cache and query data without hitting Galaxy's rate limits
- **Custom tables** — Store app-specific data (analyses, user roles, uploaded datasets) that Galaxy doesn't natively support
- **Offline-first capabilities** — Some operations can work without Galaxy being reachable
- **Performance** — Local PostgreSQL queries are faster than remote Galaxy API calls
- **Extensibility** — Add features like role-based access control (RBAC) without Galaxy changes

## Architecture

```
┌─────────────────┐     ┌───────────────┐     ┌──────────────────┐
│  Nuxt Client    │────▶│  Nitro Server │────▶│  Supabase        │
│                 │     │               │     │  ┌────────────┐  │
│ useQuery()      │     │ Effect.run   │     │  │ galaxy     │  │
│ useSupabase()   │     │ GalaxyFetch  │     │  │ galaxy_rbac│  │
└─────────────────┘     └───────────────┘     │  │ storage    │  │
                                              │  └────────────┘  │
                                              └──────────────────┘
                                                          │
                                                          ▼
                                               ┌──────────────────┐
                                               │   Galaxy API     │
                                               │   (External)     │
                                               └──────────────────┘
```

The database layer consists of:

| Schema | Purpose | Tables |
|--------|---------|--------|
| `galaxy` | Core app data | analyses, workflows, datasets, histories, jobs, instances, uploaded_datasets |
| `galaxy_rbac` | Role-based access control | roles, role_permissions, user_roles |
| `storage` | File storage | buckets, objects |
| `auth` | Supabase auth | users (reference) |

## Schema Management with Drizzle

Nuxt Galaxy uses [Drizzle ORM](https://orm.drizzle.team/) to define schemas in TypeScript:

```
packages/nuxt-galaxy/src/runtime/server/db/schema/
├── galaxy/
│   ├── analyses.ts
│   ├── workflows.ts
│   ├── datasets.ts
│   ├── instances.ts
│   ├── uploadedDatasets.ts
│   └── ...
└── galaxyRbac/
    ├── roles.ts
    ├── rolePermissions.ts
    └── users.ts
```

### Modifying the Schema

1. **Edit the TypeScript schema** in `src/runtime/server/db/schema/`
2. **Generate migration**: `pnpm drizzle:generate`
3. **Apply to local DB**: `pnpm drizzle:migrate`
4. **Generate types**: `pnpm supabase:generate:types`
5. **Commit**: Migration files (`.sql` + `snapshot.json`) are tracked in git

::warning
Never edit generated migration files in `supabase/migrations/` directly. Always modify the Drizzle schema and regenerate.
::

### Drizzle + Supabase Integration

Drizzle connects directly to Supabase's PostgreSQL via the `GALAXY_DRIZZLE_DATABASE_URL`:

```typescript
import { drizzle } from 'drizzle-orm/postgres-js'
import postgres from 'postgres'

const client = postgres(process.env.GALAXY_DRIZZLE_DATABASE_URL)
const db = drizzle({ client })
```

This works with:
- **Local Supabase**: `postgresql://postgres:postgres@127.0.0.1:54322/postgres`
- **Supabase Cloud**: Use the connection pooler for serverless compatibility

## Migration Strategy

Nuxt Galaxy uses two migration systems that work together:

### 1. Drizzle Migrations (Development)

For local development and schema iteration:

```bash
# Generate migration from schema changes
pnpm drizzle:generate

# Apply to local database
pnpm drizzle:migrate
```

This creates:
- `supabase/migrations/YYYY_MM_DD_HHMMSS_migration_name/` directory
- `migration.sql` — The actual SQL
- `snapshot.json` — Drizzle's internal state tracking

### 2. CLI Migrations (Production)

For production deployments, bundled migrations are run via the CLI:

```bash
# In production, after installing nuxt-galaxy
npx nuxt-galaxy-migrate
```

This reads `GALAXY_DRIZZLE_DATABASE_URL` and applies all pending migrations from the bundled `dist/runtime/server/db/migrations/` directory.

::note
The CLI tool is bundled with the published package, so it works without source code access.
::

### Migration Flow

```
┌──────────────────┐     ┌──────────────────┐     ┌──────────────────┐
│                  │     │                  │     │                  │
│  Schema Change   │────▶│  drizzle:generate│────▶│  Test Locally    │
│  (edit .ts)      │     │  (creates SQL)   │     │  (pnpm dev)      │
│                  │     │                  │     │                  │
└──────────────────┘     └──────────────────┘     └────────┬─────────┘
                                                           │
                                                           ▼
┌──────────────────┐     ┌──────────────────┐     ┌──────────────────┐

│                  │     │  (dist/)         │     │                  │
└──────────────────┘     └──────────────────┘     └──────────────────┘
```

## Seeding

Use the seed CLI to populate initial data:

```bash
# Create a seed config
cp node_modules/nuxt-galaxy/dist/runtime/server/db/seed.example.json seed.json

# Edit seed.json with your data

# Dry run (no changes applied)
npx nuxt-galaxy-seed seed.json --dry-run

# Execute
npx nuxt-galaxy-seed seed.json
```

### Seed Config Structure

```json [seed.json]
{
  "instances": [
    {
      "url": "https://galaxy.example.org",
      "name": "My Galaxy Instance"
    }
  ],
  "users": [
    {
      "email": "admin@example.org",
      "instanceUrl": "https://galaxy.example.org"
    }
  ],
  "rolePermissions": [
    {
      "roleName": "admin",
      "permissions": [
        "workflows.insert",
        "workflows.update",
        "workflows.delete"
      ]
    }
  ]
}
```

The seeder is idempotent — it uses `ON CONFLICT DO NOTHING` so you can run it safely on existing databases.

## Row Level Security (RLS)

All tables in the `galaxy` schema have RLS policies enabled. Examples:

| Table | Policy | Condition |
|-------|--------|-----------|
| `analyses` | User owns row | `owner_id = auth.uid()` |
| `workflows` | Public read | Everyone can view |
| `workflows` | Admin publish | `galaxy_rbac.authorize('workflows.insert')` |
| `workflows` | Admin retire, `active` the only updatable column | `galaxy_rbac.authorize('workflows.update')` |
| `workflows` | Admin delete, while no analysis references the version | `galaxy_rbac.authorize('workflows.delete')` |
| `uploaded_datasets` | User owns row | `user_id = auth.uid()` |

The `galaxy_rbac.authorize()` function checks JWT claims for role-based permissions.

## Environment Variables

| Variable | Required | Used By | Description |
|----------|----------|---------|-------------|
| `GALAXY_DRIZZLE_DATABASE_URL` | Yes | Server | PostgreSQL connection string |
| `SUPABASE_URL` | Yes | Client + Server | Supabase API endpoint |
| `SUPABASE_KEY` | Yes | Client | Supabase anon/public key |
| `SUPABASE_SERVICE_KEY` | No | Server | Service role key (for storage ops) |

Example for local development:

```bash [.env]
# Local Supabase
SUPABASE_URL="http://127.0.0.1:54321"
SUPABASE_KEY="your-anon-key"
GALAXY_DRIZZLE_DATABASE_URL="postgresql://postgres:postgres@127.0.0.1:54322/postgres"
```

Example for Supabase Cloud:

```bash [.env]
# Supabase Cloud (use connection pooler for Drizzle)
SUPABASE_URL="https://your-project.supabase.co"
SUPABASE_KEY="your-anon-key"
GALAXY_DRIZZLE_DATABASE_URL="postgresql://postgres.your-project:[password]@aws-0-[region].pooler.supabase.com:6543/postgres"
```

::warning
Never commit `.env` files to version control. Use `.env.example` as a template. Supabase keys should be rotated regularly.
::

## Type Generation

After any schema change, regenerate TypeScript types from the live database:

```bash
# Local types (from local Supabase)
pnpm supabase:generate:types

# This creates: src/runtime/types/database.ts
```

This file is auto-generated and should not be edited manually. It provides full TypeScript types for:
- Table rows
- Insert/update types
- Database enums
- Custom functions (like `galaxy_rbac.authorize`)

## Production Deployment

For production deployments:

1. **Set up Supabase Cloud** (or self-hosted)
2. **Configure environment variables** for production
3. **Run migrations**:
   ```bash
   npx nuxt-galaxy-migrate
   ```
4. **Seed initial data** (optional):
   ```bash
   npx nuxt-galaxy-seed seed.json
   ```
5. **Deploy Nuxt app** with `GALAXY_DRIZZLE_DATABASE_URL` set

::note
The migration CLI reads `GALAXY_DRIZZLE_DATABASE_URL` from environment variables automatically.
::
