## Overview

Nuxt Galaxy implements **Role-Based Access Control (RBAC)** through a custom PostgreSQL schema (`galaxy_rbac`). It integrates tightly with Supabase Auth to enforce permissions at both the database and API levels.

## Architecture

```
┌─────────────────────────────────────────────────────────────┐
│                      Authentication                          │
│                   (Supabase Auth)                            │
│                                                             │
│  User Login ──▶ JWT Token with user_role claim               │
│                 (custom_access_token_hook)                   │
└────────────────────┬────────────────────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────────────────────────┐
│                  Authorization                                │
│                   (galaxy_rbac)                              │
│                                                             │
│  Client: useUserRole() ──▶ Decode JWT claim                  │
│  Server: galaxy_rbac.authorize() ──▶ Check DB permissions   │
└─────────────────────────────────────────────────────────────┘
```

## The `galaxy_rbac` Schema

### Tables

| Table | Purpose |
|-------|---------|
| `galaxy_rbac.roles` | Role definitions (`admin`, `user`) |
| `galaxy_rbac.role_permissions` | Permission-to-role mappings |
| `galaxy_rbac.user_roles` | User-to-role assignments |

### Built-in Roles

| Role | Description |
|------|-------------|
| `admin` | Publishes, retires and deletes versions, as far as its permissions allow, and reads every user's monitoring records |
| `user` | Standard user who can run workflows and view data |

The roles are the values of the enum `galaxy_rbac.role_type`, so they are fixed. A new role means a new value of the enum and its row in `galaxy_rbac.roles`, both in a migration, and a new entry in `RoleTypes` (`src/runtime/types/nuxt-galaxy.ts`), the list the seed CLI accepts a `roleName` from.

## Custom Access Token Hook

Every time a user logs in, Supabase Auth calls `galaxy_rbac.custom_access_token_hook` which:

1. Looks up the user's role in `galaxy_rbac.user_roles`
2. Injects `user_role` into the JWT token claims
3. Returns the modified token

```json
// JWT Token Payload
{
  "sub": "user-uuid",
  "email": "user@example.com",
  "user_role": "admin", // ◀── Injected by hook
  "claims": { }
}
```

### Hook Configuration

In `supabase/config.toml`:

```toml [config.toml]
[auth.hook.custom_access_token]
enabled = true
uri = "pg-functions://postgres/galaxy_rbac/custom_access_token_hook"
```

**Permissions:** The hook runs as `supabase_auth_admin` (via `security definer`) and only that role can execute it.

## Permissions

### Permission Format

Permissions use dot notation: `{resource}.{action}`. Only three of them gate anything, all on `galaxy.workflows`:

```text
workflows.insert      # Publish a version
workflows.update      # Retire a version, or make it active again
workflows.delete      # Delete a version no analysis references
```

The enum `galaxy_rbac.role_permissions_type` has other values, such as `instances.insert` or `users.delete`, but no policy checks them, so granting one changes nothing.

### Default Permissions

The example seed (`seed.example.json`) gives the three to `admin`:

| Permission | admin | user |
|------------|-------|------|
| `workflows.insert` | ✅ | ❌ |
| `workflows.update` | ✅ | ❌ |
| `workflows.delete` | ✅ | ❌ |

The `user` role needs none: the policies on a user's own rows check who owns them, and reading workflows and instances is open to any signed-in user. Nothing else reads `galaxy_rbac.role_permissions` either: the server routes check the role's name (`requireRole`), and so does the administrator's read of monitoring records (`galaxy_rbac.is_admin()`).

### Customizing Permissions

The roles are fixed (see [Built-in Roles](#built-in-roles)), but which of the three each one holds is yours to choose. Seed them with the seed CLI, here for administrators who publish and retire but never delete:

```json [seed.json]
{
  "instances": [
    {
      "url": "https://galaxy.example.org",
      "name": "My Galaxy Instance"
    }
  ],
  "rolePermissions": [
    {
      "roleName": "admin",
      "permissions": [
        "workflows.insert",
        "workflows.update"
      ]
    }
  ]
}
```

Or insert directly:

```sql
insert into galaxy_rbac.role_permissions (role_id, permission)
select id, 'workflows.insert'
from galaxy_rbac.roles
where name = 'admin'
on conflict do nothing;
```

Neither takes a permission away: the seed CLI only adds. To withdraw one, delete its row from `galaxy_rbac.role_permissions`.

## Checking Permissions

### Client-Side: `useUserRole()`

Extract the role from the JWT token client-side:

```vue [Client Component]
<script setup>
const supabase = useSupabaseClient<Database>()
const { userRole } = useUserRole(supabase)

// userRole.value is: 'admin' | 'user' | null

const isAdmin = computed(() => userRole.value === 'admin')
</script>

<template>
  <UButton v-if="isAdmin">
    Admin Panel
  </UButton>
</template>
```

**How it works:** `useUserRole()` decodes the JWT with `jwt-decode` and reads the `user_role` claim. No database query needed.

### Server-Side: `galaxy_rbac.authorize()`

Check permissions in SQL (used in RLS policies):

```sql
-- In an RLS policy
create policy "Admin can insert workflows"
  on galaxy.workflows
  for insert
  to authenticated
  with check ((select galaxy_rbac.authorize('workflows.insert')) = true);
```

Or in server handlers:

```typescript [Server Handler]
import { ServerSupabaseClaims } from '#imports'
import { Effect } from 'effect'

export default defineEventHandler(async (event) => {
  const program = Effect.gen(function* () {
    const claims = yield* ServerSupabaseClaims
    const role = claims.user_role

    if (role !== 'admin') {
      return createError({ statusCode: 403, message: 'Forbidden' })
    }

    // Admin-only operation...
  })

  return program.pipe(
    Effect.provide(ServerSupabaseClaims.Live(event)),
    Effect.runPromise,
  )
})
```

### Row Level Security (RLS) Integration

RLS policies use both auth ID and role checks:

```sql
-- An owner reads their own analyses
create policy "Users can view their own analysis"
  on galaxy.analyses
  for select
  to authenticated
  using (owner_id = (select auth.uid()));

-- Only a role holding workflows.delete deletes a version
create policy "Admin can delete workflows"
  on galaxy.workflows
  for delete
  to authenticated
  using ((select galaxy_rbac.authorize('workflows.delete')) = true);

-- Any signed-in user reads the published workflows
create policy "Users can query workflows"
  on galaxy.workflows
  for select
  to authenticated
  using (true);
```

## User Roles Assignment

Users get their role via the `galaxy_rbac.user_roles` table:

```sql
-- Make the person who signs in as curator@example.org an administrator
insert into galaxy_rbac.user_roles (user_id, role_id)
select u.id, r.id
from auth.users u, galaxy_rbac.roles r
where u.email = 'curator@example.org'
  and r.name = 'admin';
```

New users have no role, and the seed CLI does not write `galaxy_rbac.user_roles`: assign roles as above, or in your signup flow.

## Custom Access Token Hook Function

The hook is a PostgreSQL function:

```sql
create or replace function galaxy_rbac.custom_access_token_hook(event jsonb)
returns jsonb
language plpgsql
stable
security definer
set search_path = ''
as $$
declare
  claims jsonb;
  user_role galaxy_rbac.role_type;
begin
  -- Look up user role
  select r.name into user_role
  from galaxy_rbac.user_roles ur
  inner join galaxy_rbac.roles r on ur.role_id = r.id
  where user_id = (event->>'user_id')::uuid;

  -- Inject into claims, a JSON null for a user with no role
  claims := event->'claims';
  if user_role is not null then
    claims := jsonb_set(claims, '{user_role}', to_jsonb(user_role));
  else
    claims := jsonb_set(claims, '{user_role}', 'null');
  end if;
  event := jsonb_set(event, '{claims}', claims);

  return event;
end;
$$;
```

**Security:** Only `supabase_auth_admin` can execute this function. It's revoked from `authenticated`, `anon`, and `public` roles.

## Authorization Function

The `galaxy_rbac.authorize()` function checks if the current user has a permission:

```sql
create or replace function galaxy_rbac.authorize(
  requested_permission galaxy_rbac.role_permissions_type
)
returns boolean
language plpgsql
stable
security definer
set search_path = ''
as $$
declare
  user_role galaxy_rbac.role_type;
  has_permission boolean;
begin
  -- Read role from JWT claim
  select (auth.jwt() ->> 'user_role')::galaxy_rbac.role_type into user_role;

  -- Check if role has requested permission
  select count(*) > 0 into has_permission
  from galaxy_rbac.role_permissions rp
  inner join galaxy_rbac.roles r on rp.role_id = r.id
  where rp.permission = requested_permission
    and r.name = user_role;

  return has_permission;
end;
$$;
```

## Effect Layers for Authorization

Server handlers can use Effect layers for typed authorization:

```typescript
import { ServerSupabaseClaims } from '#imports'
import { Effect, Layer } from 'effect'

// Define an authorization requirement
const requireAdmin = Effect.gen(function* () {
  const claims = yield* ServerSupabaseClaims
  if (claims.user_role !== 'admin') {
    yield* Effect.fail(new UnauthorizedError('Admin access required'))
  }
})

// Use in a handler
export default defineEventHandler(async (event) => {
  const program = Effect.gen(function* () {
    yield* requireAdmin
    // Admin-only operation...
  })

  return program.pipe(
    Effect.provide(ServerSupabaseClaims.Live(event)),
    Effect.catchAll((error) => {
      if (error instanceof UnauthorizedError) {
        return Effect.succeed(createError({ statusCode: 403 }))
      }
      throw error
    }),
    Effect.runPromise,
  )
})
```

## Migration for RBAC

The RBAC schema is created by the `galaxy_rbac_schema` migration which:

1. Creates `galaxy_rbac` schema and tables
2. Defines custom types (`role_type`, `role_permissions_type`)
3. Creates the `custom_access_token_hook` function
4. Sets up permissions (grants to `supabase_auth_admin`)

Run it via:

```bash
pnpm drizzle:migrate
# or
npx nuxt-galaxy-migrate
```
