## Overview

When extending **@gaas/ui**, the landing page (`/`) is content-driven using **Nuxt Content**. All copy, feature cards, metrics, and CTAs come from a single YAML file: `content/index.yml` in your app.

The landing page component lives in the UI layer at `packages/ui/app/pages/index.vue`. It queries `queryCollection('landing').first()` and renders the page dynamically — no code changes needed in your app.

## Architecture

```
Your App (playground/)
├── content/
│   └── index.yml                 ← Your content (canonical source)
├── content.config.ts             ← Defines the 'landing' collection
└── nuxt.config.ts                ← extends: ['@gaas/ui', '@gaas/wiki']

@gaas/ui (UI layer)
├── app/pages/index.vue           ← Landing page component
├── app/schemas/landing.ts        ← landingSchema (shared Zod schema)
└── content.config.ts             ← Default 'landing' collection (fallback)
```

## How Nuxt Content Resolves Collections

When a layer defines a collection, Nuxt Content resolves its `source` **relative to that layer's root directory**.

| Layer | Collection | Source | Resolved Path |
|-------|-----------|--------|---------------|
| Your app | `landing` | `index.yml` | `your-app/content/index.yml` ✅ |
| `@gaas/ui` | `landing` | `index.yml` | `ui/content/index.yml` |

::warning
Nuxt Content **overwrites** collections with the same name from inner layers. If your app defines `landing`, it wins. If not, the UI layer's default takes over.
::

This means:
- Your app **must** define the `landing` collection in its own `content.config.ts`
- The UI layer no longer ships default `content/index.yml` — it only provides the page component and shared schema

## Quick Start

### Step 1 — Extends layers

Your app's `nuxt.config.ts` should extend the layers:

```typescript [nuxt.config.ts]
import { dirname, join } from 'node:path'
import { fileURLToPath } from 'node:url'

const currentDir = dirname(fileURLToPath(import.meta.url))

export default defineNuxtConfig({
  extends: [
    join(currentDir, '../packages/ui'), // or '@gaas/ui' when published
    join(currentDir, '../packages/wiki'), // or '@gaas/wiki' when published
  ],
  modules: [
    '@nuxt/ui',
    '@nuxt/content',
  ],
})
```

### Step 2 — Define the `landing` collection

Import the shared `landingSchema` from `@gaas/ui` and register it in your app's `content.config.ts`:

```typescript [content.config.ts]
import { landingSchema } from '@gaas/ui/app/schemas/landing'
import { defineCollection, defineContentConfig } from '@nuxt/content'

export default defineContentConfig({
  collections: {
    landing: defineCollection({
      type: 'page',
      source: 'index.yml',
      schema: landingSchema,
    }),
  },
})
```

::note
Importing `landingSchema` guarantees your YAML data validates against the same schema the UI layer expects, ensuring type safety across layers.
::

### Step 3 — Create your content file

Create `content/index.yml` in your app's root:

```yaml [content/index.yml]
seo:

```

### Step 4 — Start the dev server

```bash
pnpm dev
```

Your landing page renders with your custom content.

## Content Reference

Each section maps to a part of the landing page. All fields are validated by `landingSchema`.

### `seo`

```yaml
seo:
  title: Page title for <title> and og:title
  description: Meta description for SEO
```

### `title`

```yaml
title: "Primary\nSecondary"
```

- The first line (before `\n`) is the primary heading
- The second line is styled with a **shimmer gradient animation**
- Use `titleSplit` (default: `\n`) to customize the split character

### `description`

```yaml
description: Short subtitle under the title
```

### `hero`

```yaml
hero:
  headline: v0.0.4 — Now with...
  links:
    - label: Primary CTA
      color: primary
      size: xl
      to: /docs
    - label: Secondary
      color: neutral
      variant: soft
      to: '#'
```

**Link properties:**

| Property | Type | Values |
|----------|------|--------|
| `color` | `enum` | `primary`, `secondary`, `neutral`, `error`, `warning`, `success`, `info` |
| `variant` | `enum` | `solid`, `outline`, `subtle`, `soft`, `ghost`, `link` |
| `size` | `enum` | `xs`, `sm`, `md`, `lg`, `xl` |
| `icon` | `string` | Icon class, e.g. `i-lucide-rocket` |
| `trailingIcon` | `string` | Trailing icon class |
| `target` | `enum` | `_blank`, `_self` |

### `logos`

```yaml
logos:
  title: Trusted by
  items:
    - i-simple-icons-vercel
    - i-simple-icons-github
```

### `features`

```yaml
features:
  headline: Capabilities
  title: Your headline
  description: Brief explanation
  items:
    - icon: i-lucide-workflow
      title: Workflow Execution
      description: Run Galaxy workflows with real-time status tracking
    # ... up to 6 items, displayed in a 3-column grid
```

### `metrics`

```yaml
metrics:
  headline: By the numbers
  title: Built for scale
  description: Context for the metrics
  items:
    - value: '99.9%'
      label: Uptime
      class: text-success
    - value: <50ms
      label: Query time
      class: text-primary
```

`class` should be a Tailwind text color utility: `text-{color}-{shade}`.

### `cta`

```yaml
cta:
  title: "Ready\nto integrate?"
  description: Get started with GaaS today
  command: pnpm dlx nuxi init my-gaas-app
  links:
    - label: Get started
      color: primary
      to: '#'
```

The `command` field is optional. When present, a **copy button** appears next to CTA links.

## Editing Content with Nuxt Studio

When running the dev server, you can edit `content/index.yml` in real time using **Nuxt Studio**.

### Setup

1. Ensure `nuxt-studio` is in your modules (enabled in `@gaas/wiki` by default)
2. Start the dev server: `pnpm dev`
3. Open the Studio URL in your browser
4. Navigate to the Editor and locate `content/index.yml`
5. Edit — changes are reflected instantly

### How it works

Nuxt Studio writes directly to `content/index.yml` in the **running app's directory**. Because your app defines the `landing` collection, the edited file is the canonical source.

::warning
Nuxt Studio edits the **app's** `content/index.yml`, not the UI layer's. This is why your app must define the `landing` collection — to tell Nuxt Content where to look.
::

### Playground as a Template

The `@playground/` app serves as a **living template** for new projects. It demonstrates:

- How to extend `@gaas/ui` and `@gaas/wiki`
- How to define the `landing` collection
- How to structure `content/index.yml`
- How to include wiki and bibliography collections alongside landing

When starting a new project, copy the `playground/` directory as a starting point and customize `content/index.yml`.

## Importing Shared Schemas

Both `@gaas/ui` and `@gaas/wiki` export shared Zod schemas that downstream apps can import:

```typescript
// From @gaas/ui
import { landingSchema } from '@gaas/ui/app/schemas/landing'

// From @gaas/wiki
import { bibliographySchema, wikiPageSchema } from '@gaas/wiki/app/schemas/wiki'
```

This keeps validation logic in one place while allowing each app to define its own collections.

## Troubleshooting

### Changes in `content/index.yml` are not reflected

- Verify your app's `content.config.ts` defines the `landing` collection
- Clear Nuxt Content cache: `rm -rf .data/ .nuxt/`
- Restart the dev server

### "Maximum call stack size exceeded"

This is a known issue with certain heavy dependencies (e.g. `shaders` package with extensive exports). The fix: wrap the component in a dynamic import:

```vue
<script setup>
const HeroShaders = defineAsyncComponent(() =>
  import('~/components/HeroShaders.client.vue')
)
</script>
```

### "Cannot read properties of undefined (reading 'headline')"

The landing page component expects `page.hero.headline` to exist. Ensure:
- `content/index.yml` contains a `hero:` block
- The `landing` collection is properly loaded (check `[@nuxt/content] Processed X collections` in dev output)
