## What a results view is

A **results view** is the component you write to display the results of an **analysis**, one execution of a **workflow** requested by a user. GaaS matches the view to the analysis's workflow by the workflow's name and **version**, the two values its author wrote as `name:` and `version:` tags in Galaxy.

Users reach it at `/analyses/:id/results`, below the panel that lists the analysis's inputs and outputs as they arrive.

The view receives the analysis already loaded: its workflow row, its inputs and its outputs, each carrying its dataset and its tags. A results view never queries the analysis itself before rendering.

## Where the file goes

Put the component at `app/workflows/<name>/<version>/results.vue` in your app, a fixed path named after the workflow's two tag values. `<name>` and `<version>` are the `name:` and `version:` tag values **written exactly as tagged**, case and dots included. For a workflow tagged `name:satelliteFinder` and `version:0.11`, the file is `app/workflows/satelliteFinder/0.11/results.vue`.

The playground ships three views, one for each rung described below:

```
app/
└── workflows/
    ├── results.vue                  # every workflow of the application
    └── satelliteFinder/
        ├── results.vue              # every version of satelliteFinder
        └── 0.11/
            └── results.vue          # satelliteFinder, version 0.11
```

::warning
Matching is exact. `satellitefinder` does not stand for `satelliteFinder`, and `0.1.1` does not stand for `0.11`. Copy the two values from the workflow's tags in Galaxy rather than retyping them.
::

Other files can sit next to `results.vue`, such as a helper component the view imports. Only the file named `results.vue` is registered.

## Which view applies: the rungs

A **rung** is how specifically a view names the workflows it applies to. When an analysis is opened, the rungs are tried from the most specific down and the first file found is rendered:

| Rung | File | Applies to |
|------|------|------------|
| Exact | `app/workflows/<name>/<version>/results.vue` | One workflow: this name and this version |
| Name-level | `app/workflows/<name>/results.vue` | Every version of the name that has no exact view |
| App-wide | `app/workflows/results.vue` | Every workflow of the application that has neither |

When no file matches, the **generic results view** GaaS ships is displayed instead (see below).

A view can live in a layer as well as in the app. When the app and a layer it extends both define a view of the same scope, the app's applies, as for every other Nuxt convention, and the development server says once which file was shadowed.

## What the view receives

Every results view declares the same props, imported from `#gaas/ui`, an alias the `@gaas/ui` layer declares for its public types. The import has to be explicit: Vue resolves a `defineProps` type only through an import in the file.

This is the playground's name-level view, verbatim, and the smallest view worth writing:

```vue [app/workflows/satelliteFinder/results.vue]
<script lang="ts" setup>
import type { ResultsViewProps } from '#gaas/ui'

// The name-level results view (ADR 0003): it applies to every version of the
// `satelliteFinder` workflow that has no `satelliteFinder/<version>/results.vue`
// of its own, and to no other workflow name.
const props = defineProps<ResultsViewProps>()

const workflow = computed(() => props.analysis.workflows)
</script>

<template>
  <div>
    <h1 class="text-xl font-bold">
      {{ workflow.name }} <VersionBadge :version="workflow.version_key" />
    </h1>
    <p class="text-sm text-muted">
      Name-level results view for <code>{{ workflow.name_key }}</code>, applied to version
      <code>{{ workflow.version_key }}</code>: {{ analysis.analysis_outputs.length }}
      output{{ analysis.analysis_outputs.length === 1 ? '' : 's' }}.
    </p>
  </div>
</template>
```

`computed` and `VersionBadge` are auto-imported by Nuxt, as in any page of your app; only the props type needs its import line.

| Prop | Type | What it carries |
|------|------|-----------------|
| `analysisId` | `number` | The analysis the view is opened on, as the route names it. |
| `analysis` | `ResultsViewAnalysis` | The analysis row with its workflow, inputs and outputs. |

Inside `analysis`:

- `analysis.workflows` is the workflow row, with `name`, `name_key` and `version_key` (the two tag values as stored at activation), `galaxy_id` and `definition` among its columns.
- `analysis.analysis_inputs` and `analysis.analysis_outputs` are arrays with one shape: each element is the row (`id`, `dataset_id`, `state`, ...) with `datasets`, the dataset row (`dataset_name`, `storage_path`, ...), and `tags`, its tag rows (`label`).

The three types are exported from `#gaas/ui` too, should a helper component need them:

```ts
import type { AnalysisInputWithDatasetAndTags, AnalysisOutputWithDatasetAndTags, ResultsViewAnalysis } from '#gaas/ui'
```

### Reading the files themselves

The prop names the datasets; the files live in Storage. Downloading them is up to the view, in the browser, on top of the rows the prop already lists. The playground's exact view does it with `analysisDatasetsQuery`, which answers with a pair: the input files first, the output files second, each next to its row.

```vue [app/workflows/satelliteFinder/0.11/results.vue]
<script lang="ts" setup>
import type { ResultsViewProps } from '#gaas/ui'
import type { Database } from 'nuxt-galaxy'

const props = defineProps<ResultsViewProps>()

const supabase = useSupabaseClient<Database>()
const { data } = useQuery(() => analysisDatasetsQuery({ analysisId: props.analysisId, supabase }))

const outputFiles = computed(() => data.value?.[1] ?? [])
</script>
```

Each element of `outputFiles` is `{ entry, blob }`: the output row and its contents as a `Blob`, ready for `blob.text()` or a parser of your own.

::note
A registered view renders in the browser only, inside an error boundary. A view that throws shows an error message in its place, and the analysis page around it keeps working.
::

## The tag rule enforced at activation

Since a view is found by a directory named after the two tag values, each value has to be a legal directory name. When an administrator activates a workflow, GaaS refuses a `name:` or `version:` tag value that does not match `^[A-Za-z0-9][A-Za-z0-9._-]*$`: letters, digits, dots, hyphens and underscores, starting with a letter or digit. Galaxy itself only strips whitespace from a tag, so a `/`, a `+`, a space or a leading dot get through Galaxy and are refused here.

For a workflow tagged `version:0.11+galaxy2`, nothing is activated and the administrator reads, next to the switch on the admin workflows page, a toast titled **Workflow not activated**:

> The `version:` tag value `0.11+galaxy2` cannot name a results view directory. Use letters, digits, dots, hyphens and underscores, starting with a letter or digit.

Fix the tag in Galaxy, then activate again. A value that passes is stored exactly as tagged, case included, in the workflow's `name_key` and `version_key`; those are what an analysis is matched with.

Workflows activated before this rule keep the keys they were stored with and simply have no view: the generic results view shows for their analyses.

## The generic results view

An analysis whose workflow matches no file shows the generic results view. Users read one line and nothing else, since the inputs and outputs are already listed above it:

> This workflow has no dedicated results view yet.

The development server adds an alert titled **Shown by the development server only**, spelled with the workflow's own tag values:

> Create `app/workflows/<name>/<version>/results.vue` to give this workflow a results view.

Production shows the one line only. When you see the alert, create the file it names and navigate to the analysis again.

## The Results view column

The admin workflows page has a **Results view** column that says, for every workflow carrying both tags, what its analyses will get:

| Reading | Meaning |
|---------|---------|
| `exact` | A view names this workflow's name and version. |
| `fallback` | A name-level or app-wide view stands in for it. |
| `none` | The generic results view shows. |

The registry is built from your directories, so the column answers for workflows that are not activated yet: write the directory, open the page, and check the row before anyone activates the workflow. A row that should read `exact` and reads `none` is a directory that matches no workflow, usually a tag spelled differently from the directory. Once a workflow is activated the column reads the keys stored at activation.

## Development mode

The registry of views is generated at build time by scanning every layer's `app/workflows/` directory. With the development server:

- The startup log lists what was found, `<name>/<version>` for an exact view, `<name>/*` for a name-level one and `*/*` for the app-wide one. For the playground tree it reads `Results views: */*, satelliteFinder/*, satelliteFinder/0.11`.
- Creating or removing a view while the development server is up regenerates the registry; the change shows up on the next navigation. Editing a view's contents is ordinary hot reloading.
- A view that loses to another layer's view of the same scope is announced once: `Results view <file> is shadowed by <file>`.

## Adding a view, step by step

1. In Galaxy, read the workflow's `name:` and `version:` tags. Check they pass the rule above.
2. Create `app/workflows/<name>/<version>/results.vue` from the snippet above, spelling both directories exactly as tagged.
3. Open the admin workflows page: the workflow's row reads `exact`.
4. Open an analysis of that workflow at `/analyses/:id/results`: your view renders where the generic results view was.

## Why directories

The mechanism this replaces derived a component name from the two tag values, which lost information: stripping dots made `0.11` and `0.1.1` one component, and lowercasing the name made a misspelling fall silently to the generic results view. Directory names carry the identity exactly as tagged, the registry is typed, and each view is loaded on first render. The reasoning and the options considered are recorded in [ADR 0003](https://github.com/rplanel/GaaS/blob/main/docs/adr/0003-results-view-directory-convention.md).
